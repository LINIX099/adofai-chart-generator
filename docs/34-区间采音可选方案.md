## 1. 现状（照代码抄的，不是回忆）

### 1.1 数据模型

```jsonc
state.regions = [
  { "start_ms": 19155, "end_ms": 35127,
    "tracks": [3],              // 用哪几条轨（可多选，取并集）
    "label": "B段" }
]
```

### 1.2 语义（`sidecar/session.py::apply_regions`）

```
区间内：**先把全局 onset 整段丢掉**，再放进「区间自己的 tracks 采出来的那一批」
区间外：全局结果原样保留
重叠  ：后写的赢（因为上一步是"整段丢掉"）
收尾  ：按 `merge_ms` 去重 —— **只留最早的那个**
边界  ：`t0 <= o.t_ms < t1`（左闭右开）
```

它**只改「采哪些音」**，不碰几何/时序 ⇒ 求解器/模板/雪花/双押全部无感。
这是现状里最值得保留的一点。

### 1.3 交互

| 入口 | 现状 |
|---|---|
| 全曲预览条 | `Shift + 拖动` 框选 → `onRegion(t0,t1)`；**长度 < 60ms 直接丢弃**（静默） |
| 「＋ 加区间」 | 固定在播放头 `−2000ms ~ +6000ms`（**写死的魔法数**） |
| 编辑器 | 名字 / **起止毫秒**（`type=number step=100`，旁边显示 `(12.34s)`）/ 用轨 chips / ✕ |
| 换文件 | `state.regions = []`（**直接清空，不可保存/复用**） |
| 状态栏 | 「区间 N 段（M 段生效 / 共采 K 点）」 |

### 1.4 全局其实已经有**三个角色**

`② 音轨` 里是三个列表：**主轨**（并集全采）/ **次级轨**（只在主轨空白 > `sub_gap_ms` 处补）
/ **双押轨**（不参与并集，只用来标双押落点）。

而区间**只能改第一个角色**。

## 2. 为什么「数毫秒」难用 —— 逐条，都有代码依据

### P1 · 时间是绝对毫秒，没有音乐含义
你想的是「从小节 17 起」，界面上只能填 `19155`。整个回传链路（`payload.regions` /
`region_spans`）也都是 ms。

### P2 · 定边界的精度是**像素级**，而边界语义是硬切
- 框选把像素映射回毫秒（`_evTime`）；全曲压缩视图下 **1px ≈ 几十~上百 ms**；
- 起点还 `Math.round()` 取整，而匹配是 `t0 <= o.t_ms < t1`
  ⇒ **差 1ms，边界上那个音头就进不来 / 被丢掉**；
- 预览条上拖动看不出「我到底切在哪个音上」。

### P3 · ★ 病根是**先聚类、后切割**（原稿的说法已按实测修正）
原稿写：「整段丢掉 + 放进自己的 + 按 `merge_ms` 去重且只留最早」三步叠起来，
边界两侧各有一个 onset 且相距 < `merge_ms` 时，**必被合并掉一个**。

**这句是错的**：那一对音在**单趟并集**里本来就会被并成一个（`build_onsets`
的簇条件就是「距簇头 ≤ `merge_ms`」），所以「少一个」不是老算法的错。

**真正的错**在 `apply_regions` 与 `build_onsets` 的**调用顺序**上：

```
老做法：  聚簇（整条轨）→ 按边界筛掉簇外的音      ← 簇头被筛走 ⇒ 整簇消失
正确口径：按边界挑音    → 聚簇                     ← 边界不参与聚类
```

实测（`tools/_seg_probe.py`，20000 组随机「3 轨 + 一个区间」）：

| | 例 1 | 例 2 | 例 3 |
|---|---|---|---|
| 老做法 | `[40, 70, 260]` | `[50, 260, 450]` | `[60, 240, 530]` |
| 先切后聚 | `[40, 260]` | `[50, 220, 260, 450]` | `[30, 80, 240, 530]` |
| 症状 | **凭空多 1 个** | **吃掉 1 个** | **吃掉 1 个** |

**555/20000（2.8%）**的结果不同，**双向**出错。另有一个 off-by-one：老尾巴
去重用 `<`、片内聚类用 `<=`，于是「恰好相隔 `merge_ms`」的跨边界一对会**多留一个**。

而边界本身**不是一个音乐事件** —— 它只是个像素换算出来的数字。

### P4 · ★ 最本质：**角色不是时间的函数**
- 想表达「这一段把钢琴降为次级」：得把钢琴从**主轨**里去掉、加进**次级轨** ——
  但次级是**全局**的，做不到「这一段」；
- 想表达「这一段只留节拍器」：只能靠区间覆盖，但区间**只有主轨这一维**，
  次级/双押仍然是全局的 ⇒ 组合表达不出来。

### P5 · 编辑成本高、体验毛糙
- 「＋加区间」开在 ±2s/+6s（猜测值）；没有吸附、没有复制、没有「沿用上一段的轨集」；
- 改一个数字就 `renderRegions()` **重建整个列表**（输入框焦点/光标会跳）；
- 名字默认「区间N」，但预览条上宽度 < 26px 就不画标签。

### P6 · 表达不了「开区间」
真实编辑里绝大多数是「**从第 N 小节开始，往后都用这几条轨**」。
现在必须手动算出「结尾毫秒 = 曲子长度」。

### P7 · 换文件即失效、且不可保存
`doLoad` 里清空，没有导出/导入，也没法把「这首歌的编排」存下来复用。

## 3. 候选方案

### 方案 A · 吸附到「格 / 拍」（最小改动）
保留 `[start_ms, end_ms)`，只改**输入与吸附**：
- 显示/编辑改成 **`#格号` / `小节:拍`**，内部仍存 ms；
- 框选时**吸附到最近的格边界**（`overview` 已有 `floorAt` / `floorTime`，直接用）；
- 数字框旁边加 `←`/`→` 逐格微调；去掉那个隐形的 60ms 门槛（或写明）。

> 改动面：**只动前端**（`app.js` + `views/overview.js`）。后端零改。
> 解决：P1、P2、P5（部分）。
> 不解决：**P3、P4、P6、P7**。

### 方案 B · A + **开区间**（仍是小改动）
区间变成半开终点：

```jsonc
{ "from": 34, "until": 61 | null, "tracks": [3], "label": "B段" }   // null = 到结尾
```
UI 默认「到下一段为止 / 到结尾」，只有你拖右边界才显式收口。

> 解决：P1、P2、P5、**P6**。 不解决：P3、P4、P7。

### 方案 C · ★ **音轨角色时间轴**（per-track role lanes）—— 推荐
**把「区间」这个概念消掉**，换成**每条轨一行泳道**，泳道上画块，块给这条轨一个角色：

```
        ┌─────── 全曲预览条（现有 canvas，加高即可）───────┐
trk0 主 ┃██████████████████┃            ┃████████████████┃
trk1 次 ┃      ▓▓▓▓▓▓▓▓    ┃            ┃                ┃
trk2 主 ┃      ████████████┃            ┃                ┃
trk3 关 ┃                  ┃            ┃▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓┃
trk4 dp ┃                  ┃▓▓▓▓        ┃                ┃
        └────────────────────────────────────────────────┘
         0s                20s          40s           60s
```

- 三档角色：**主**（全采，进并集）/ **次**（只在主轨空白 > `sub_gap_ms` 处补）/ **关**
- **没画块的地方继承全局 ② 的选择** ⇒ 完全向后兼容（不画 = 今天的行为）
- 主轨集合 = 该时刻所有 `主` 的轨 → 并集；次轨集合 = 该时刻所有 `次` 的轨 → `notes_fill_gaps`

**为什么它是最本质的解法**：
- **P4 消失**：角色变成时间的函数，三个角色都随时刻变；
- **P3 消解**：不再有「整段丢掉再插入」，任何时刻只做**一次并集**——
  「这个音属于哪条轨」「这条轨此刻在不在采」两件事都确定，
  **不会因为边界落在哪儿而凭空产生/消灭一个 onset**；
- **P2/P6/P5/P7 顺带解决**：拖块天然可吸附到格、可拖到结尾（开区间）、
  块可复制/拖拽；数据就是一份可序列化的编排表；
- **布局成本低**：预览条本来就预留了一条「区间色带」的高度（`bandH`），
  扩成 N 行泳道只是把它乘以轨道数 + 加高 canvas。

**代价 / 要定的语义**：
1. 块**重叠**怎么算（同一轨两个块叠上：后者赢？取并集？）；
2. 块边界是否强制吸附格/音头；
3. `② 音轨` 那三个 chips 列表要不要保留（作为「全局默认」）—— 我倾向**保留**；
4. 改动面最大：`schema` / `session`（`apply_regions` 重写为按时刻查角色）/
   `overview` 渲染 + 命中测试 / `app.js` 编辑器 / `test_sidecar` 的区间 15 条断言 / 文档。

> **「区间」是它的一种特例**：一段「把 trk0 关掉、把 trk3 打开」的块。
> 旧数据可由后端**编译**成泳道 ⇒ 平滑迁移，不用一次性改完前端。

### 方案 D · 「按 onset 归属改写」（选区模型）
在卷帘/下落式里**框选若干 onset**，再指定这批点的来源。
> 优点：完全不碰边界（用户选的永远是具体的音）。
> 缺点：**本质是"结果编辑"而不是"规则编辑"** —— onset 是派生量，改任何上游参数就全废；
> 大段落要选几千个点。**不推荐单独用**，可作为泳道之上的补充微调。

### 方案 E · 「锚点 / 标记」+ 区间引用
先打点（marker，吸附到最近格），区间 = `[A, B)` 按名字引用。
> 解决 P1/P2；**P4 仍不解决**；多一个概念。价值主要在「同一处反复引用」。

## 5. 我的建议：**已按 C 一步到位**（原建议是 B→C 两步）

原建议（保留作记录）：1) 先做 B（开区间 + 吸附，只动前端）；2) 再做 C（泳道角色）。

**实际执行改了主意**：B 的价值基本被 C 覆盖（C 的最后一段天然到曲末 =
「往后都用这几条轨」），而且 C 的表达是 B 的**超集**；分两步做只会把
「边界语义」这件事改两遍。所以**直接上 C**，代价是改动面大（`core/segments.py` +
`session` + 预览条 + 面板），但因为**区间路径原样保留**（有分段才让位），
回退是零风险的。

> 落地件：`docs/39-分段采音.md`；核心 `core/segments.py`；体检 `tests/test_segments.py`。

## 6. 要你拍板的（**只剩第 1 个还悬着**）

1. **你实际用区间采音时，高频道场景是哪几种？**
   （① 一段换成另一条轨 · ② 一段**多**加一条轨 · ③ 一段把某轨**降级**为次级 ·
   ④ 一段只留节拍器/鼓 · ⑤ 一段完全静音不采）
   —— **已按「三档 × 三态（继承 / 关掉 / 显式）」实现，不需要第四档**；
   但如果你发现 ①~⑤ 里有哪种被这套模型表达得别扭，请说，我加第四档。
   推荐你在 UI 上先试这五种，看有没有一种是「画不出来」的。
2. **边界希望吸附到什么？** → 已定：**不强制吸附**（对齐用「取播放头」按钮 +
   全曲条的格导航完成，`docs/34` P2 的像素问题因此消失）。
3. **要不要能跨文件保存复用？** → 已定：**能**（分段就是 `state` 里一份
   JSON，跟着界面状态一起存/载；导出工程时一并带上）。
4. **双押轨、次级轨要不要也纳入时间轴？** → 已定：**纳入**（三维都可随时间变）。
5. **布局**：→ 已定：**复用全曲预览条那块画布**（扩成一条轨一行的泳道），
   编辑器仍在 ② 音轨分区里（紧挨区间编辑器下面）。
6. 旧 `regions`（毫秒）**要不要保留兼容读取**？ → 已定：**保留**，
   但**一旦有分段就整个忽略并报警告**（不静默丢用户已经画好的东西）。
