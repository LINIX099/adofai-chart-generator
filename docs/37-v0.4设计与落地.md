```
        ┌────────────── 音轨（第一类对象）──────────────┐
来源： MIDI 轨 │ 音频检测（xk base）│ BDG 工程 │ 手工点
角色： 主 / 次 / 双押 / 关      ← 角色随区间变化（= 泳道模型）
        └──────────────────┬──────────────────┘
                           ▼  onsets + 约束
        solve()（BPM 表 · 双押需求 · 预留槽位 · Δ 预算）
                           ▼
                        .adofai
```

**BDG 的编辑器就是我们的泳道编辑器**（`docs/35` §3.6：角色写在 `track.type` 上）⇒
`docs/34` 里最贵的那块 UI **可以不写**。这是把三件事并成一次大版本的核心理由。

## 3. ★ 「以我们为准」的正确边界（**已按实测定稿**）

原设计（`docs/35` §3.4 初稿）说「把我们的 tempo 表写进宿主 `bpmPoints`」—— **错的**，会造成事故。

```
timeMs = timeOfBeat(beat)          // 它是 baseBpm / offsetMs / bpmPoints 的函数
```

改宿主的 `bpmPoints` / `offsetMs` ⇒ **他工程里所有 marker 的 `timeMs` 集体平移、与音频脱钩**。

| | 谁说了算 | 怎么做 |
|---|---|---|
| **`beat ⇄ ms` 的锚**（`baseBpm`/`offsetMs`/`bpmPoints`） | **BDG**（他对着波形对的轴） | **只读**，当**双向换算器** |
| **音乐内容**（SetSpeed / 双押 / 图形 / Δ 预算） | **我们** | 写进**插件自己的 BPM 轨**的 marker + `attrs`，不碰宿主 `bpmPoints` |
| 两边冲突（宿主 `bpmPoints` 不是 no-op 且有实质变速） | —— | **报出来让人选**，不偷偷改 |

**为什么这样反而更准**：`timeOfBeat` / `beatOfTime` 段内互逆（已实测误差 **0.00e+00**），
我们只要把算好的**毫秒**用他的 map 反解成 `beat` 交过去，他再转回来就精确还原 ——
**不需要两张表长得一样**。

> **「以我们为准」= 谱面的音乐内容以我们为准；「音频与拍号的对齐」以 BDG 为准。**
> 这条边界原方案搞反了。

## 4. 第一步带回的**契约**（写进测试，不许回退）

| 事实 | 断言 |
|---|---|
| `beat` 是「用平铺 map 编码的毫秒」，**不在任何吸附网格上** | 866/866 不是 0.25 的倍数；`0.0064` 未被 round；`time_of_beat(0.0064) = 1327.0ms`（= 2.0ms 的音） |
| **两套 BPM 并存** | 宿主 `bpmPoints` = `mult×1`（no-op）；真变速在插件轨 `attrs`：`multiplier ×2 @ 8.0064 / 64.0064` |
| `loop` 语义 | 92 母点 / 391 子点；`子点数 = count − 排除数`；`exclude` 就是 `k` 本身；悬空数 **0** |
| `beat` 不唯一 | 232/866 是重复 beat ⇒ **解析/写回绝不去重**（去重只在 onset 判定） |
| 记录稀疏多变 | 点 4 种键组合 / 轨 2 种 / 有**空轨**/ 类型化轨**没有** `hidden` |
| 角色载体 | 普通轨 → 主；未知类型化轨 → **非音轨**（含 `bpm`/`twirl`），并记一条「猜测」 |

**循环子点的关键细节**：上游快照里子点**已经显式存在**（`store.refreshChildren` 真的建 marker）
⇒ `expand` 默认 **`synth_only`：只补缺**，实测「补出 0 / 已有 391」；补出来的点带 `synth=True`
⇒ **emit 不写回**（写回去只会制造重复）。

## 5. 第二步：`/ws` 桥（**已完成**）

### 5.1 形态（`docs/35` §3.2 有硬证据）

**我们 sidecar 当服务端；BDG 的 `renderer.js` 当客户端。**
理由：宿主的 `main.js` 里 `ctx` **没有渲染层回推通道**，主进程当服务端只能单推；
而 `renderer.js` 在主世界、原生 `WebSocket` 可用。

```
BDG(renderer.js) ──WebSocket──► sidecar/server.py /ws ──► core.bdg.parse()
   api.events.on("project") / api.project.snapshot()   api.project.edit.batch(...)
```

### 5.2 交付的两个模块

| 文件 | 干什么 | 关键点 |
|---|---|---|
| `sidecar/ws.py` | **最小 RFC6455 服务端** | 只用标准库；握手 Accept 向量、7/16/64 位长度、**客户端掩码必解**、分片拼接、ping 自动 pong、close 收场；单帧/单消息都有上限 |
| `sidecar/bridge.py` | **协议层（传输无关）** | `handle_text(str) → [str]`，所以能脱 socket 单测；`serve(conn)` 只管循环 |

接线只有三处：`App.__init__` 生成一次性 token + `Bridge`；`GET /ws` 升级；
`GET /api/bridge` 把 `ws://127.0.0.1:PORT/ws?token=…` 暴露给界面；启动时打印同一串。

### 5.3 消息层 v1（全量）

| 方向 | type | 载荷 | 我们的处理 |
|---|---|---|---|
| BDG→我们 | `hello` | `{v, token, plugin, bdg, caps}` | 回 `accepted{accepted:[1], root, caps}`；**版本超出只 warn 不拒** |
| BDG→我们 | `project` | `{project}` | ★ 走**同一个 `core.bdg.parse()`**（`docs/36` §9） |
| BDG→我们 | `selection` / `playhead` / `audio` | 选择 / 试听拍位 / `system.audioPath()` | 记住 + `ack` |
| 我们→BDG | `pull` / `import` | 请求全量 / 把我们算好的写成他的轨 | `pull_msg()` / `import_msg()` 已可用 |
| 双向 | `ping`/`pong` / `ack` | 心跳 / 写操作回执 | **每次写操作都回执，不许静默** |

**`project` 的回执把解析报告原样回给对端面板**（命中别名 / 默认 / 猜测 / 重复拍 / 是否可写回）
—— 让 BDG 那边也看得见我们怎么看他的工程。

```
回执示例：ok=True  n_tracks=6  n_points=866  n_bpm_events=2  dup_beats=232
         parser=standard · fmt=2 · 别名命中=27 · 默认=4 · 猜测=2   can_emit=True
```

**空快照不 ok**：`{}` 会被 generic 兜底接住，`can_emit=False` ⇒ `ack{ok:false}` 并说明理由
（**绝不把「解出来是空的」当成功**）。

### 5.4 安全

- **只听 `127.0.0.1`**（`--host` 默认值）；
- **一次性 token 在升级握手之前校验**（同机任何程序都能连上本地端口，宿主的文档还明说
  「安装插件即视为信任、不弹权限确认」⇒ 校验是**我们**的责任）；比较用 `hmac.compare_digest`；
- 对端数据一律当**外部输入**：单帧 8MB / 单消息 8MB 上限、未协商 RSV 位直接拒、
  坏 JSON / 未知 `type` 一律 `ack{ok:false}` + 记账；
- 状态可查：`GET /api/bridge`（`state()`：connected / authed / peer / 点数 / parser / 上次警告）。

### 5.6 ★ 写回吸附：**已按宿主源码定案**（我第一版读错了，这是更正）

**真代码**（`vendor/beat_data_generator`，proxy 拉下来的）：

```ts
// store.ts:315,317-319
const round = (b: number): number => Math.round(b * 1e6) / 1e6;   // ★ 1e-6 精度，不是整拍！
function snapped(b: number): number {
  return store.ui.snapEnabled ? snapBeat(b, store.ui.snapDiv) : round(b);
}
// store.ts:736-744  ★ 这就是用户说的「也可以不吸附」
export function moveMarker(id: string, rawBeat: number, force = false): boolean {
  ...
  const beat = Math.max(0, force ? round(rawBeat) : snapped(rawBeat));
// tempo.ts:109-112
export function snapBeat(beat: number, div: number): number {
  if (div <= 1) return Math.round(beat);        // div=1 才是整拍
  const step = 1 / div; return Math.round(beat / step) * step;
```

⇒ **三种写入的精度完全不同**（我原来把「关吸附」和「div=1」混成一件事，错了）：

| 情形 | 公式 | 精度 / 损失 |
|---|---|---|
| 吸附开 `div=1` | `Math.round(beat)` | **整拍**，最坏 0.5 拍 ≈ 156ms |
| 吸附开 `div=4`（常见档） | 吸到 1/4 网格 | 866/866 被挪，最坏 0.1186 拍 = **37.06ms**，**23 点超 25ms 预算** |
| 吸附开 `div=16` | 1/16 网格 | 866/866 被挪，最坏 8.65ms |
| **吸附关** | `round(b*1e6)/1e6` | **1e-6 拍 ≈ 0.3µs ⇒ 实践上无损**（20/866 点动 ≤0.0001ms） |
| `moveMarker(..., force=true)` | `round(b*1e6)/1e6` | 同上，但**插件 API 没暴露 `force`** |

**⇒ 结论变了**：

- **`0.0064` 的来源找到了** —— 它就是**关吸附**路径写的（`round()` 把 beat 量化到 1e-6 拍）；
  不是「第三条神秘路径」；
- **写回无损是可行的**，条件是**用户在 BDG 里关掉吸附**（或宿主把 `force` 暴露给插件 API）；
- 但按 §1.b 的新口径 **v0.4 根本不需要写回** ⇒ 吸附问题**不再是拦路石**，
  只作为「将来要做写回时」的前置条件记在 `core/bdg/snap.py` 与 `tools/_bdg_snap_audit.py` 里。

## 7. 明确不做

- ❌ **不 fork 宿主**（GPLv3 传染 + 技术栈不同 + 它没有求解能力）；
- ❌ 不做「格式嗅探猜版本」的玄学 —— 只认**候选路径 + 能力探测**，命中什么写进报告；
- ❌ 不做「自动修复写入」（会把用户的工程改坏）：**兜底模式拒绝写回**；
- ❌ 不读它的 TypeScript 类型做代码生成 —— **只按概念解析**（`docs/36` §10）。

> 收束：**我们依赖的是「概念」（拍 / 轨 / 环 / 变速 / 属性），而不是「字段」。
> 概念的名字可以换，概念本身不能。**
