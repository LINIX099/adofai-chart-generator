## 三、为什么「现有逻辑」默认跑出来不像人写的

先用默认参数跑一遍（`out/osn1_v1`）：**直线 79.1% · Twirl 0.08 · 多押 1.4% · SetSpeed 9.7**。
四个原因，全部实测定位：

### ① 时间戳来源**强制直拟合**，而直拟合的基准 BPM **参数化不了**

`sidecar/session.py` 在 `fit_mode == direct`（时间戳来源的默认）时走
`core/fitdirect.py::build`，基准 BPM 传的是

```python
base_bpm=(self.xk_cbpm or float(self.denoise_meta.get("bpm") or 0.0))
```

—— **`SolveParams.base_bpm` 一个字都没读**。所以 `--set auto_bpm=False --set base_bpm=330`
**完全不生效**（实测 `params_solve` 正确返回 330，产物还是 660）。
**唯一能改的入口是 `denoise_hint_ms`（= 砖长 ms）**：`60000/330 = 181.818182`。

### ② 等间隔输入 + 直线优先 ⇒ 必然全场直线

`gain = 直线?1:0 − speed_penalty·|log2 k|`。8 分密集段 `r ≡ 0.5` 时：

| 候选 | gain |
|---|---|
| `travel=180 k=0.5`（**降一半速换直线**） | 1 − 0.35 = **+0.65** |
| `travel= 90 k=1`（照常转 90°） | 0 − 0 = **0.00** |

⇒ DP 全场选前者。**这就是 79% 直线的来源，也是 `0.5x 占 28.6%` 的来源。**
真人反着来：Renewed 的 `v=0.5` 有 63.7% 落在 **k=1**（转 90°），`0.5x` 只有 2.7%。

### ③ 模板库一条都没匹配上

`patterns/templates.json` 里 `A_均分骨架_A2 = notes[0.5,0.5] → travel[90,90]`
**正是为「等间隔音符」写的**。但基准取成 660 时 `rs ≡ 1.0`，和 `notes=0.5` 差一倍 → 0 命中。
另外 `template_max_span_s = 10.0` 这道闸要求「段落 ≤ 10 s」，而本曲旋律**几乎没有休止**
（`template_rest_ms=300` 切不开）⇒ 整曲算一个 128 s 的长段落 ⇒ 连三连音以外的模板**全被拒**。
（这一条**本次没有动** —— 它属于「模板要不要在长段落里工作」的设计问题，见 §6。）

### ④ `straighten`（回正）会把 Twirl **清光**

回正的 DP 在**偏轴量相同**时选 Twirl 最少的那条。90°/180° 为主的路径
**本来就全在正交轴上**（deviation ≡ 0）⇒ 有没有 Twirl 偏轴量都是 0
⇒ DP 当然选「0 个图标」。实测 `straighten=False` 时 Twirl 从 **0 → 21**。

## 四、改了什么（两个通用旋钮，默认值 = 老口径逐字节不变）

### `SolveParams.slow_speed_penalty`（schema 新字段「降速档额外代价」）

`k < 1` 时**每个八度**额外扣分（在 `speed_penalty` 之外）。
`0.0` = 老口径。实测 `r=0.5` 要翻盘需要 > 0.65（= 1 − `speed_penalty` 0.35）。

只罚**变慢**，加速档一个字节不动。理由来自语料：P12~P15 的 `0.5x` 只占 0.6~5%，
同曲参照 2.7%，而我们的默认路径 28~32%。

### `SolveParams.speed_min_run`（schema 新字段「一档至少连续几层」）

core 里**一直有**、sidecar **从没接线**（`p.speed_min_run` 只在 `_merge_short_runs`
里被读，UI 传不进去）⇒ 死参数。默认 `6` = 老口径。

★ 接线时**没有出现新代码路径**：`params_solve` 本来就把 `SolveParams` 的默认值 6 传了下去，
现在只是允许用户改。

## 六、说清楚：**没做到的**与**为什么**

1. **SetSpeed 1.61 远低于同曲参照的 25**。
   参照的 25/100 来自「短促地插一格 2x / 1.333x / 1.5x」——
   那需要 **1.333x / 1.5x** 这些非 2 的幂档，而 `SPEED_TIERS` 只有 2 的幂。
   **这是一处结构差异，不是参数没调好**：我们的 120°/135° 因此写不出来
   （参照谱 120° 11.0% + 135° 5.9%，我们只能拿 101.25°/78.75° 近似）。
   要补的话是「把 `SPEED_TIERS` 扩成 `2^a·1.5^b`」——**属于改设计，本次没动**。

2. **`101.25° / 78.75°`（各 3%）是「碎渣」**。
   来源：检测器的帧量化是 **5.805 ms**，而 90.909 ms 的砖长**不是它的整数倍**
   ⇒ 真实间隔在 87.1/92.9 ms 之间抖，去噪把其中一小撮吸到 ±1 格（11.36 ms）上。
   `aggressive_fit`（15° 阶梯 + 拟合容差）能把它整成 **105°/75°**（都在 15° 整数倍上、
   1/12 网格 100%），代价是**动时值**。本次**没有开** —— 用户口径是「时序优先」，
   而且 101.25/78.75 本身就在 1/12 网格上（1/12 网格 88.4%）。

3. **模板 0 段 / 覆盖 0 格**（§3③）。本次没动 `template_max_span_s`。
   本曲几乎没有休止 ⇒ 整曲是一个长段落 ⇒ 模板闸全关。**这是待办，不是结论。**

4. **midspin 0%**（语料中位 0.43%，但**同曲参照也是 0**）。
   45 张里有 21 张是 0。判定「在带内」靠 P10=0 通过的。

5. **演出层很重**：`MoveTrack 3539 条`（每格 `in_init`+`in_ret`+`出A` 三条），
   参照谱只有 17 条。这是「入场 / 离场演出」的默认产物，**视觉上不空但文件 1.45 MB**。
   要精简：`--set show_schedule=False`。
