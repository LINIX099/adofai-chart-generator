# 41 · 桥接三问：诊断与修法

> 用户 2026-10 拿真谱（`out/FallenEra`）试桥之后提的三件事：
>
> 1. **桥接丢过去的轨道不是「踩点轨道」**
> 2. **初始 BPM 几乎完全不一样，只能靠猜**
> 3. **只要我们这边变了速，编辑器那边直接就对不上音**
>
> 本文只用**实测数据**说话。复现脚本：`tools/_fallenera_diag.py`、`tools/_adofai_diag.py`、
> `tools/_subdiv_check.py`、`tools/_anchor_live.py`。

***

## ★ 结论速览（已落地）

| # | 状态 | 修法 |
|---|---|---|
| 1 | ✅ 已修 | 插件改用 **`addTrack({name})`（内置踩点轨）**，不再用 `addTypedTrack` |
| 2 | ✅ 已修 | 载荷带上**我们的时序锚**（`baseBpm`/`offsetMs`），由插件 `setBaseBpm`+`setOffset` **先设再算拍位**；每点改发 **`ms`** |
| 3 | ⏸ 按用户口径**先不修** | 他那边**没有**采音/鼓点处理；「细分」实测**可行**：`baseBpm` 取谱面 BPM 时**1/1 就精确**（我们变速是 2 的幂）。真遇到任意 BPM（如那份参考谱）才需要他那 1 行 |

## ★★ 真机又踩出两个 bug（单测没抓到，值得记）

### A. 内置轨的 `type` 是 **`"beat"`**，不是空串 ⇒ 每次投射都新建一条轨

第一版的 `findTrack` 写成 `if (!t.type && t.name === name)`。
**宿主快照里内置轨的 `type` 是 `"beat"`** ⇒ 这个条件**永远不成立** ⇒
每次投射都 `addTrack` 一条新的，`spec.clear` 也就永远清不掉上一批。

实测后果：**推两次 = 两条 `ADO·主轨` + 24 个点**（越推越乱）。

假宿主当时写的是 `type: ""`，所以单测全绿 —— **假宿主和真宿主不一致，等于没测**。
现在假宿主已经对齐成 `"beat"`，并加了「连推三次：轨数仍是 1、点数仍是 3」的回归断言。

### B. `n_off_grid` 把**浮点误差**当成「被挪」

判据写的 `> 1e-9`。整拍点的 beat 会有 `2.0000000000000004` 这种 ε 噪声 ⇒
实测报 **「5 个点被挪」而 `drift_max_ms = 0`** —— 自相矛盾、还很吓人。

改成宿主自己的精度（它内部就是 `round(b*1e6)/1e6`）：`> 1e-6`。
现在整拍点是 `n_off_grid = 0`。

***

## 1. 轨道不是「踩点轨道」—— 我们的错，**已修**

我们的插件用 `api.project.edit.addTypedTrack(P + ":" + role, name)` 建轨
（`bridge_plugin/renderer.js` 的 `applyImport`），也就是**注册了插件轨类型**。

而宿主的 `plugin-api.d.ts` 里，一个插件轨类型**没有**任何「继承内置踩点轨行为」的字段：

```ts
interface TrackTypeSchema {
  id: string;
  trackName: LocaText;
  pointName: LocaText;
  color?: string;
  fields: PluginField[];      // ← 没有 basedOn / extends / kind
}
```

⇒ **插件轨永远不可能是内置踩点轨。** 用户的观感完全正确。

**修法（我们这边，不动宿主）**：改用内置轨 —— API 里有：

```ts
addTrack: (opts?: { name?: string }) => string;     // ← 内置踩点轨
addTypedTrack: (typeKey: string, name?: string) => string | null;   // ← 我们一直在用这个
```

即：**按角色建几条「内置轨」，名字还是 `ADO·主轨 / 次轨 / 双押轨`**，但 `type` 是
内置的 `beat` ⇒ 它们是**真正的踩点轨**，用户能用编辑器全套工具（加/删/挪、吸附、播放…）。

角色怎么认？两条腿：
* 每条点的 `attrs.adbRole` 是权威（`setMarkerAttrs` 是**合并**写入，挪点不丢）；
* 找轨时按 **名字**（名字被改了就按「轨上有没有带 `adbRole` 的点」兜底）。

> `role_for_type()` 那套「从 type 冒号后面认角色」就**只留给读别人的工程**了 ——
> 对我们自己投过去的点不再适用（它们现在是内置轨）。

## 2. 初始 BPM 对不上、只能靠猜 —— 我们的错，**已修**

**根因**：我们的 import 载荷里**根本没有时序锚**。`build_import` 原来只出：

```python
{ "run": ..., "tracks": [ {"role","name","clear","onsets":[{"idx","beat","attrs"}]} ] }
```

没有 `baseBpm`、没有 `offsetMs` —— 我们**只推了拍位**。
所以宿主留在它自己的 `120 / 2101`，用户看到的就是 120，只能猜。

**用户口径**：「这个 bpm 和偏移是我写的，只能粗略对音」⇒ 他那两个值**不是权威的**，
所以用**我们的**：`bridge_anchor()` 取的就是导出 `.adofai` 里 `settings.bpm / settings.offset`
（`writer.build_json(ch.base_bpm, offset_ms=st['offset'])` 同一对来源）。

⚠️ 这里还有一个**没测**的候选：我们的 offset 是**采音轴**上的，他的 `offsetMs` 是
**他的音频轴**上的。若两者差一个前置静音，会表现成**常数**偏移（与变速无关）。
`FallenEra` 那份我们的 `offset=0`、他的 `2101` —— 差 2.1s，需要真机看一眼点落没落在波形上。

## 3. 一变速就对不上音 —— ★ 按用户口径**先不修**，但「细分」实测可行

### 3.1 他的 tempo 模型**支持**绝对 BPM 变速

`src/renderer/src/tempo.ts:19-45`：

```ts
curBpm = p.mode === "abs" ? clampBpm(p.value) : clampBpm(curBpm * p.value);
```

### 3.2 但他的**插件 API 不给设值**（这是那 1 行的缺口）

`store.ts:869` 是**三参数**：

```ts
export function addBpmPoint(rawBeat, mode: BpmMode = "abs", value?: number) { ... }
```

插件层包装（`plugins/api.ts:320`）把它**写死成两参数**：

```ts
addBpmPoint: (beat) => addBpmPoint(beat)?.id ?? null,   // ← mode/value 全被丢掉
```

⇒ 建出来的是「继承当前 BPM」的**空操作**点（这正好解释了 v0.4 实测的 `bpmPoints = mult{1}`）。
`setMarkerAttrs` 走 `findMarker` 只认 marker，补不了；自建插件 bpm 轨宿主的 tempo **不读**。

最小改动 1 行 + 1 个类型（要用时再上）：
```ts
- addBpmPoint: (beat) => addBpmPoint(beat)?.id ?? null,
+ addBpmPoint: (beat, mode, value) => addBpmPoint(beat, mode, value)?.id ?? null,
```

### 3.3 他那边**没有**采音/鼓点处理（已查）

`grep 采音|鼓点|onset src/ plugins/` → **0 处**。他是纯手工编辑器，
没有「采音鼓点加速」这类处理可以借。

### 3.4 但「细分」这条路**通**，而且比 32 分音更省

他的吸附档在 `src/renderer/src/metrics.ts:10`：

```ts
export const SNAP_DIVISIONS = [1, 2, 4, 8, 16, 32] as const;
```

而且 `ProjectBar.vue` 的 `parseSnapDenominator` 是**自由分母**（`/^(?:1\/)?(\d+(?:\.\d+)?)$/`，
任意正数都收）。⇒ 1/32 只是预设之一，要更细也能手输。

**实测（`tools/_subdiv_check.py`，拿真谱算「精确落格」而不是「分辨率够」）**：

| 谱 | 档位 | 比值 | `baseBpm` 取**最高档**（= 谱面 bpm） |
|---|---|---|---|
| **我们生成的** `main.adofai` | {180, 360} | 1 : 1/2 | ★ **1/1 就精确**（0.000ms） |
| 那份参考谱 `FallenEra/main.adofai` | 13 档（`220.0002`/`290.0003`…） | 无理 | ⚠ 到 1/256 仍然 **0% 精确落格** |

★ 为什么我们这么容易：**我们变速的档位是 2 的幂**（`solve` 强制的）⇒
`谱面BPM / 档位` 多半是整数 ⇒ 所有点都落在**整拍**上，**连细分都不用调**。
真机复核也印证了：`beats = [0,1,2,…,11]` 全是整数。

> 所以 **#3 的正确退路不是「换算成 32 分音」，而是「把宿主 baseBpm 设成我们谱的 bpm」**。
> 只有像那份参考谱那样用**任意 BPM**（220.0002…）时，细分才真的不够，还得上 bpmPoints。

### 3.5 顺带：谁先设锚的**顺序坑**（已修）

原设计是**我们**算 `beat = beat_of_time(ms)` 再发拍位，而**锚在宿主那边** ——
只要他之后一改 BPM，那批拍位全废。这正是「一改就对不上」的另一半。

现在改成：载荷同时带 **`ms`** 和 `beat`，**插件**在「锚设好之后」用宿主当前模型
换算拍位（`beatOfTime`）。真机断言过：若顺序错了，`1000ms/2000ms` 会算成 `-2/-1` 拍而不是 `0/3`。

## 4. 一个重要的运维概念：**junction ≠ 热更新**

`tools/host.js link` 做的是 junction，省掉的是「重装插件」这一步 ——
**但不省「重载宿主页面」**。宿主的渲染层是 Vite 起的 dev server，它**不会**热更新
`root` 之外（junction 出去）的路径。

实测：改完 `bridge_plugin/renderer.js` 后继续推，宿主跑的**还是旧代码**
（回执里没有 `anchor`/`via_ms`，还在每次新建轨）。`location.reload()` 之后才对。

顺手补了一个体验问题：**插件现在记住地址就自动重连**（以前每次重载都要人点一下
面板里的「连接」，而「重载」恰好是开发中最常做的事）。
