### 0.3 ★★ 本轮最重要的结论

**① 和 ② 是一对硬冲突的指标：**

* ② 数的是「我们的按键里有多少**落在 MIDI 音头**上」；
* ① 要的是「我们发出**比 MIDI 音头更多**的按键」（参考谱 2543 vs MIDI 独立音头 1774）。

⇒ **任何「凭空补出来的键」都会同时抬高 ①、压低 ②。**
实测：补格把 ① 抬到 76.2%，代价是 ② 从 100% 掉到 69.6%。

**唯一能同时满足两者的机制是「双押」（同一时刻两个键）** —— 因为两个键都落在同一个
MIDI 音头上，② 不降；而参考谱里**有 514 组「30 ms 以内的按键对」**（`docs/71` §3），
第二个键正好能认领其中一对的另一半。
用户 2026-10 说的「**通过双押轨道（用分段采音辅助的）进一步加强**」正是这条路。
实测 `flower_dp`：① **66.5%**（比基线 +6.1）、② **97.1% ✅** —— 两条都变好，**① 仍差 80%**。

**为什么双押也补不满**：双押只能落在**已有 onset 的时刻**上，而参考谱那 966 个「多出来的
按键」里有 411 个在 **onset + 1/8 拍**、243 个在 **+1/4 拍**（§5）—— 双押放不到那里。
要在 ① 上到 80%，必须发出 **2035** 个匹配对；把双押铺满全部 1741 个 onset 会让分母涨到
3482，一对一反而掉到 **59.9%**。**最优只到 ~70%。**

## 1. ★★ 尺子 bug：② 的 84.3% 是假的，真值 **99.9%**

### 1.1 现象

`docs/71` §0.5 记了一条「② 的偏移搜索可疑」：同一份产物，
带 `--chart-offset` 搜到 **−60 ms → 99.9%**、不带时 **+106 ms → 84.3%**。

### 1.2 根因：**两条时间基，差一个「首音时刻」**

| 量 | 起点 |
|---|---|
| `chart_key_times()`（谱面） | **0 ms** —— 谱面是**本地轴**（第 0 层是开局站位，parser 把它的角行程置 0） |
| `midi_key_times()`（MIDI） | **913.04 ms** —— MIDI 是**绝对轴**（第一个音头在 913.04 ms） |

拿本地轴去比绝对轴 = **凭空加 913 ms 的整体平移**。±600 ms 的搜索范围**够不着**，
所以停在了一个假的局部最优上。

### 1.3 为什么它没有「悬崖」把自己暴露出来

**913.04 ms 恰好是 130.4348 ms（460 BPM 的砖长）的整数倍**（913.04 = 7 × 130.435）
⇒ 两条轴**在粗网格上仍然对得齐** ⇒ 偏移曲线「到处都还行」，看不出来。

★ 教训与 `docs/71` §2.1 那条「看到悬崖就先怀疑 offset」是一对：**这次是没有悬崖，所以也得查。**

### 1.4 修法

`tools/align_chart_midi.py` 新增 `anchor()`：**把 MIDI 平移到「第一个按键 = 0」再比**。
锚定后 `generated[j]` 与 `midi_onset[j]` 的偏差 **≤ 0.31 ms**（全员），② 直接 **99.9%**。

★ **谱面 ↔ 谱面那一侧不需要也不应该再动** —— 两边本来就都是本地轴（都以自己的第一个按键为 0）。
★ `--midi-absolute` 可以关掉锚定（对照用）。

## 2. ★ 尺子的第二个 bug：判据不能用「搜出来的偏移」

### 2.1 现象

补格产物 `out/flower_fill` 有一批键**正好落在「离最近音头 32.571 ms」**上（> 30 ms 容差）。
`--accept` 的 ② 原来会**搜一个让覆盖最大的偏移**，搜到 **+3 ms** 之后

```
|32.571 − 3| = 29.571 ≤ 30   ⇒ 全部算「对上了」   ⇒ ② 虚报成 **100.0%**（真值 69.6%）
```

### 2.2 修法

**判据钉在「真对齐」（偏移 0）上；搜出来的偏移只报不判**，并且在报告里写明它可能
「把边界情况削进容差」。

★ 这是一条通用的量尺纪律：**任何「为了凑指标而搜索的对齐参数」，都只能当情报，不能当判据。**

## 3. ★ 补格（`core/tilefill.py`）—— 「分段采音设置采bpm」

### 3.1 为什么需要

参考谱 **2543** 键 / 768 拍 = **3.31 键/拍**；我们 **1742** / 768 = **2.27 键/拍**。
一条 onset 一格 ⇒ 我们**永远追不上**。参考谱的按键相对最近 MIDI 音头的落点（锚定后实测）：

| 落点 | 占比 |
|---|---|
| **正好在 onset 上** | 71.6% |
| **onset + 1/8 拍** | **16.2%** |
| **onset + 1/4 拍** | **9.6%** |
| +3/8 拍 | 0.1% |

⇒ 参考谱在**够长的间隔里按 bpm 网格再铺几格**，落点几乎只有 +1/8 和 +1/4 两档。

### 3.2 架构：与 `core/xkbase.py` 同一条路 —— **注入合成 onset，不改 `solve()`**

`xkbase` 已经证明这条最省（`docs/47` §3）：往 `onsets` 里塞 `Onset(..., synth=True)`，
**下游求解 / 写盘 / 反解校验一行都不用改**。本模块只做**更保守**的一件事：

* **一个真实 onset 都不丢**（`xkbase` 是区间内全丢换成骨架砖）；
* 只在「相邻两个真实 onset 之间**离得够远**」时才补；
* 补点落在 `t = a + k·(砖长/div)` 上 —— **锚在间隔起点**，不是全局网格，
  所以不会因为全曲 bpm 微漂而跟参考谱错开。

### 3.3 砖长（= 采bpm）**不另造一套**

直接复用 `core.denoise.plan`（间隔对数直方图众数 → 周期精修 → 取整齐值 → 置信度）。
**另造一套就等于有两个「采bpm」会说不同的话。** 测不出来 ⇒ **一格都不补**并把原因写进 `why`，
**不猜一个砖长硬上**（不许静默）。

### 3.4 ★★ 和弦门：本轮最有用的那一档（实测依据）

在 ADOFAI 里，**同时响的几个音没法一次按完**，所以人手会把和弦**摊开**成连续的几格。
实测（Flower Rocket，1740 个间隔）—— **间隔起点被参考谱补过点的比例**：

| 间隔起点的和弦大小 | 间隔个数 | 被补的比例 |
|---|---|---|
| 1（单音） | 605 | **18.0%** |
| 2 | 370 | **43.8%** |
| 3 | 139 | **68.3%** |
| 4 | 318 | **57.5%** |

⇒ `fill_min_merged=2` 只补和弦起头的间隔（把单音那 18% 的噪声挡掉）；
`fill_per_chord=True` 再把上限设成「和弦大小 − 1」（n 个音摊成 n 格）。

### 3.5 参数与实测（`--set fill_div=…`）

| 参数 | 默认 | 含义 |
|---|---|---|
| `fill_div` | **0 = 关** | 砖长切几份（2 / 4 / 6 / 8）。**0 ⇒ 逐字节不变**（老路径） |
| `fill_min_steps` | 3 | 间隔短于「几份」就不补（太小会把八分音符也切碎） |
| `fill_max_per_gap` | 1 | 每个间隔最多补几个。**0 = 铺满**（实测铺满把命中打到 41%） |
| `fill_min_merged` | 1 | **和弦门**：间隔起点至少几个同时音 |
| `fill_per_chord` | False | 按和弦大小摊开 |
| `fill_max_add` | 20000 | 上限；撞了**记在账上**（不静默截断） |

**实测（真实导出 + 反解校验）**：

| 配置 | 键 | 覆盖 | 一对一 | ② | 几何 |
|---|---|---|---|---|---|
| 基线 | 1742 | 82.0% | 60.4% | 99.9% | ✓ |
| `d4 s3 g1 弦门2` | 2504 | 84.0% | **76.2%** | 69.6% | ✗ 占地 3.8 |
| `d2 s2 g1 弦门2`（落点改中点） | 2504 | **90.3%** | 68.7% | 69.5% | ✓ 占地 120.9 |
| `d4 s3 g2 弦门2` | 3266 | 92.2% | 65.8% | 76.7% | ✗ |

## 4. ★★ 为什么 ① 到不了 80%（硬证据）

### 4.1 上限算术

```
一对一 = 匹配数 ÷ max(两边条数)
基线：max(2543, 1742) = 2543，匹配 1537 ⇒ 60.4%
要 80% ⇒ 匹配 ≥ 2035
```

### 4.2 三个「不可能」

1. **只发 1741 个键（= MIDI 的独立音头数）⇒ 数学上限 68.5%。**
2. **补到 2035 个键也不行** —— 实测「把每个够长的间隔按 1/8 拍铺满」得 3083 键，
   覆盖冲到 94.1%，但**命中只有 59.8%** ⇒ 一对一 **59.8%**（不升反降）。
3. **规则全扫过一遍**（均分细分 18 组、纯网格填充 5 组、按间隔门控补点 30 组）：
   **最好 69.2%**（= 间隔 ≥ 3/8 拍时补一个 1/8 拍点）。真实导出后是 **76.2%**。

### 4.3 差距全在「补哪儿」这个信息上（oracle 实验）

把**参考谱自己的补点位置**喂进去（不可实现的上限）：

```
键 2770 | 覆盖 100.0% | 命中 92.6% | ★一对一 91.8%
```

⇒ 只要知道「哪些间隔被补过」，就能到 91.8%。但：

```
间隔 2/8 拍：638 个，被补 254（39.8%）
间隔 4/8 拍：964 个，被补 458（47.5%）
间隔 8/8 拍：108 个，被补  65（60.2%）
```

**一半补、一半不补，而区分它们的特征不在 MIDI 里**（试过：和弦大小 ✓ 有信号、
音长 ✗、发音数 ✗、音符密度 ✗、局部偏移 ✗、note-off ✗）。

## 5. 双押轨道（用户点名的第二条路）

```powershell
python tools\gen_from_source.py '<midi>' --tracks 0 --json 'dp_checked=[1]' `
  --ref '<参考谱>' --set offset=883 --out-dir 'out\flower_dp'
```

★ `--json` 是**本轮新加的参数**：`--set` 的 `coerce` 只出标量，
`dp_checked` / `xk_ranges` / `segments` 这些**列表 / 字典型状态键根本传不进去**
（`--tracks` 当初就是为这一个键开的口子，现在补成通用形式）。

实得：`1 轨 → 1247 onset；1918 层`，**双押 670 处**（反向 665 / 正常 5），
丢 272 处（撞模板/引擎/雪花 270）—— **丢的账都报出来了**。

| | 基线 | **`flower_dp`** |
|---|---|---|
| 键数 | 1742 | 1918 |
| 覆盖 | 82.0% | 73.1% |
| ★ 一对一 | 60.4% | **66.5%** |
| ② | 99.9% ✅ | **97.1% ✅** |

★ **注意 `--tracks 0,1` + `dp_checked=[1]` 与 `--tracks 0` + `dp_checked=[1]` 输出完全相同** ——
`_selected()` 会把「已分给双押泳道的轨」从主轨里摘掉。这是对的，但**要在报告里说明**。

## 6. ★ 代价：几何会碎

| 产物 | 直线率 | 每格占地 | 几何体检 |
|---|---|---|---|
| 基线 | 68.0% | 354.2 格² | ✓ 像一条路 |
| 补格 `d4 s3` | 8.5% | 3.8 格² | ✗ **碎渣** |
| 补格 `d2 s2` | 56.3% | 120.9 格² | ✓ 像一条路 |
| 双押轨道 | 7.5% | 1.9 格² | ✗ **碎渣** |

**根因（实测）**：补出一个 32.6 ms 的短格时，求解器**不用高档位走直**，
而是留在 230 BPM 用 `travel=22.5°`（≈157.5° 的发卡弯）去凑时间：

```
基线   f3 travel= 90.0 bpm=230    （130.4ms，一个直角）
补格后 f3 travel= 22.5 bpm=230    ← 32.6ms 的发卡弯
       f4 travel= 67.5 bpm=230    ← 97.8ms
```

全程 2280/2504 层都压在 230 BPM。`SPEED_TIERS` 里**有 ×8**，但 DP 的
`speed_penalty=0.35`（「抑制 ×8 这种极端档」）把它罚掉了。
⇒ **下一轮的第一件事**：给「短格」一条豁免（优先直 + 允许高档位），
而不是靠调 `straight_weight`（那个是**预设制**的，`schema` 里只能选档，传数值没用 —— 实测 3/6/12 输出完全一致）。
