# 02 · 角度限制澄清：「15° 限制」是我搞错了

> **结论：你是对的。`angleData` 是浮点数组，没有 15° 限制。**
> 我上一版把 15° 当成速度天花板，是把 **legacy `pathData` 的字符表** 误当成了 **现代 `angleData` 的格式约束**。
> 本文把错误来源、正确事实、以及**真正需要注意的那个坑**全部列清楚。

---

## 一、我错在哪（诚实复盘）

错误推理链：
1. 我读了 `parser/angle.py` 开头的 `Angle_Correspondence` 字典 —— 一张 `'p'→15.0, 'J'→30.0, …` 的表，
   只到 15° 一档。
2. 我又只看了一张谱（CLionSister），它的角度正好几乎都是 15° 的倍数。
3. 于是我把「**这张谱的习惯**」+「**那张表**」= 得出了「15° 是格式上限」的结论。

**两处都错了**：
- `Angle_Correspondence` **只用于 legacy `pathData`**。`angle.py` 第 41-44 行写得清楚：
  ```python
  try:
      self.angleData = ald.result["angleData"]        # ← 现代格式：直接用，不查表
  except KeyError:
      path_data = ald.result["pathData"]
      self.angleData = [self.Angle_Correspondence[char] for char in path_data]   # ← 只有这里查表
  ```
- 一张谱说明不了格式。**要下格式结论必须扫全部语料。**

## 二、正确的事实链（附证据）

### 证据 1：游戏里 `angleData` 就是 `List<float>`
`‹游戏反编译源码目录›\ADOFAI\LevelData.cs:24`
```csharp
public List<float> angleData;
```
序列化在 `LevelData.cs:476`：`dictionary.Add("angleData", angleData.ToArray());`
读取在 `LevelData.cs:580`：`angleData = new List<float>(RDEditorUtils.DecodeFloatArray(dict["angleData"]));`
→ **单精度浮点数组，无任何量化。**

### 证据 2：15° 只属于 legacy `pathData`
`ADOFAI\FloorHelper.cs` → `TryGetPathInDegrees(char pathId, out float angle)`：
```
'R'=>0, 'p'=>15, 'J'=>30, 'E'=>45, 'T'=>60, 'o'=>75, 'U'=>90, 'q'=>105, 'G'=>120, 'Q'=>135,
'H'=>150, 'W'=>165, 'L'=>180, 'x'=>195, 'N'=>210, 'Z'=>225, 'F'=>240, 'V'=>255, 'D'=>270,
'Y'=>285, 'B'=>300, 'C'=>315, 'M'=>330, 'A'=>345, '!'=>999
```
这是**字符串格式**（v≤12 谱面的 `pathData`）：**一个字符 = 一个固定角度 → 这里 15° 才是硬限制。**
`MigratePathData()` 把这种老谱面转成 `angleData` 浮点数组后，这个限制就消失了。

### 证据 3：语料实测 —— 6% 的角度根本不是 15° 的倍数
扫描 `‹社区语料目录›\` 全部 521 张谱的 `angleData`：

```
角度数值总数 = 779,765
非 15° 倍数 = 46,591  (5.98%)   样例: -340, 160, 140, -20, 160, 20, 40, 200, ...
小数位分布: 0位×742210, 1位×12863, 2位×7769, 6位×4562, 3位×4309, 7位×3245, 4位×2550, 5位×1331, 8位×214, 10位×8, 9位×2
```

- 有 **702 个值是科学计数法**（`dec=99`），说明精度远超 15°。
- 有**2 个值精确到 9 位小数**、**8 个到 10 位小数**。
- `-340`、`160`、`140`、`20` 这些**整数但非 15 倍数**的值大量存在。

→ **15° 是作者的书写习惯（94% 是整数度，其中大多数凑在 15° 档），不是格式约束。**

### 证据 4：时间上角度一律 mod 2π
`scrMisc.cs:373-389`
```csharp
public static double GetAngleMoved(double entryAngle, double exitAngle, bool isCW) {
    float num = (isCW ? 1f : (-1f));
    return mod((exitAngle - entryAngle) * (double)num, 6.2831854820251465);   // mod 2π
}
public static double AngleToTime(double angle, double bpm) {
    angle = mod(angle, 6.2831854820251465);
    return angle / 3.1415927410123742 * bpm2crotchet(bpm);
}
```
（`mod` 定义在 `scrMisc.cs:305`：`return (x % m + m) % m;` —— 负数也归一到正）

→ **>360° 的“多圈角”不加时间**：`532.5°` 与 `172.5°` 对时间等价。
→ 所以角度对时间的**有效取值区间就是 `(0°, 360°)`**。

## 三、真正的坑（这条比 15° 重要得多）

`scrLevelMaker.cs` 的两个函数里都有同一段：

```csharp
// CalculateSingleFloorAngleLength()
double num3 = Math.Abs(num2);
if (num3 <= 1E-06 || num3 >= 6.283184307179586) {
    if (cf.midSpin) { num2 = 0.0; }
    else            { num2 = 6.2831854820251465; cf.turnaround = true; }   // ← 整圈掉头 = 2 拍
}

// CalculateFloorEntryTimes()
if (angleMoved <= 1E-06 || angleMoved >= 6.283184482025146) {
    num4 = (scrFloor3.midSpin ? 0.0 : (2.0 * timeBetweenAngles));          // ← 同上
}
```

**读法：**
| 角行程 | 结果 |
|---|---|
| `≈ 0` 且 **非中旋** | ⚠️ **不是瞬时！被强制变成 360°（= 2 拍）的掉头层** |
| `≈ 0` 且 **中旋(999)** | ✅ 0 拍，真正的“同瞬间” |
| `≈ 360°` 且 **非中旋** | ✅ 整圈掉头，2 拍 |
| `(1e-6 rad, 2π-1e-6 rad)` | 正常，时长 = `deg/180 × (60000/bpm)` ms |

**角行程的可用下界 = `1e-6 rad ≈ 5.73e-5°`**。
在 180 BPM 下 = 1.06e-4 ms ≈ **0.1 µs**。

→ **格式上的速度上限 ≈ 无限。** 我上一版说的「56 音/秒」完全是错的。

## 四、这对生成器设计的影响（方案变更）

| | 旧方案（基于错的 15° 假设） | 新方案（基于上述事实） |
|---|---|---|
| 密集音怎么处理 | 必须抬 `SetSpeed` 的 BPM，否则丢音 | **直接把 Δt 写进角度**，`span = Δt_ms × bpm / 333.333`，任意精度 |
| 需要防护什么 | —— | **「角行程下限守卫」**：任何落进 `(0°, 5.73e-5°)` 或 `(360°−5.73e-5°, 360°)` 的层，必须改判为**中旋 999** 或重排，否则游戏会静默把它变成 2 拍长层 |
| 同瞬间多音怎么表达 | 未考虑 | **中旋 999** 是唯一正确手段（0 拍） |
| 什么时候才需要 `SetSpeed` | 密集段 | 只在**需要改变基准拍速**时（比如 MIDI tempo 变化、或想让角度回到可视美观区），不是速度上限问题 |
| 角度的自由度 | 15° 一档 | **任意浮点**；只在**视觉美观**上建议向 15°/整数度靠 |

**唯一还需要注意的“软”约束**（不是格式，是观感/编辑器）：
- 编辑器拖动时默认按 15° 吸附（所以 94% 的谱是整数度）；
- 角度太小的层在画面上几乎看不出旋转，观感上像 bug —— 这是**美术判断**，不是格式限制；
- 所以生成器应该提供「**美观量化**」开关（如吸附到 1°/15°/整数度），**默认关闭或可调**，而不是硬编码。
