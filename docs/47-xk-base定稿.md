## 0. 一句话

**把「谱面基础 = 一拍几砖（N）」从求解器手里收回来交给用户**；
而因为「大直线」这个定义，它**同时**把**落块策略**（无视 onset，硬铺）和**采音输入**
（主轨失效、其余只当多押）一起换掉 ⇒ **是主干改造，不是加一个参数**。

## 2. tbpm 链（含那个站的算法实证）

### 2.1 那个站到底怎么算的（已查实）

`vocalremover.org/zh/key-bpm-finder` 的 BPM **不是服务器算的，是在浏览器里用 WASM 算的**
（所以「抓源码」的正解是**装同一个公开库**，不是爬接口）。逐行断点反编译的记录见
[Rean's Blog · vocalremover 测 BPM 的算法](https://rean-schwarze.github.io/p/3f13b766/)，实际调用：

```
PCM（双声道 → 逐样本平均成 mono）
  → 简易「区间平均」重采样到 16 kHz
  → Essentia.arrayToVector(…)
  → PercivalBpmEstimator(vec, 1024, 2048, 128, 128, 210, 50, 16000)
```

= **[Essentia](https://pypi.org/project/essentia/)（MTG/UPF）的 `PercivalBpmEstimator`**。
把参数对到[官方头文件](https://github.com/MTG/essentia/blob/v2.1_beta5-1389-g36ec3d92/src/algorithms/rhythm/percivalbpmestimator.h)
上（JS 侧是**字母序**传参）⇒ **它全是默认值，只把 `sampleRate` 换成 16000**：

| 参数 | 该站 | 库默认 |
| --- | --- | --- |
| frameSize | 1024 | 1024 |
| frameSizeOSS | 2048 | 2048 |
| hopSize | 128 | 128 |
| hopSizeOSS | 128 | 128 |
| **minBPM** | **50** | 50 |
| **maxBPM** | **210** | 210 |
| **sampleRate** | **16000** | 44100 |

### 2.2 ★ 由此得到两条必须做的防护（不许静默）

1. **八度夹取**：`minBPM 50 / maxBPM 210` ⇒ 该站输出**被夹在 [50, 210]**，超过 210 的曲子会给
   **half-time**（240 → 120、300 → 150）。而 `cbpm = tbpm × N` ⇒ **tbpm 错一个八度，整条骨架全错**。
2. **交叉校验**：把「tbpm × N」得到的砖长，与**去噪解出的 `period_ms`** 比；差 **×2 / ÷2**（或其它整数倍）
   就**直接报出来**，绝不悄悄采用。

### 2.3 落地路线（C 已实测走不通）

| 路线 | 结论 |
| --- | --- |
| **A 手填** | ✅ 打底方案。输入框 + 「打开该站」按钮（`shell.openExternal`）+ 取整规则写在旁边 |
| **B Electron 侧跑 `essentia.js`（WASM）** | ★ **唯一能离线复现同一个数的方案**（同库同算法）。`essentia.js@0.1.3`，解包约 **10.1 MB** |
| **C Python 侧 `pip install essentia`** | ❌ **实测不行**：开发机 `python 3.14.3 / win32`，`pip index versions essentia` = `No matching distribution found`；PyPI 上只有 **manylinux + macosx** 轮子，**无 win_amd64** |
| D 用现有 `librosa` / `gridfit` | ⚠️ **数值不会一致**，会跟那个站对不上 ⇒ 更乱，不用 |

⇒ **默认自动填充（B）+ A 手填兜底**；B 以**侧载**形态提供（见 §7）。

### 2.4 我们现有的是什么（别混）

| 现有 | 干什么 | 与那个站的关系 |
| --- | --- | --- |
| `sidecar/schema.py` 的 `auto_bpm`（默认开） | 「求解器**自己挑八度**」（`base_bpm` 留 0，由 `solve()` 内部定） | ★ **这正是 xk base 要取代的** —— 它是**猜**，不是检测 |
| `core/gridfit.py` + `core/denoise.plan()` | 从 **onsets** 反推周期 `period_ms` + 相位 `phase_ms` | **事后反推**，且要求已有 onsets；**不是**听音频给 tbpm |
| MIDI 源自带的 `mbpm` | MIDI 文件里的 tempo | **只有 MIDI 有**；OGG / 音频没有 |

⇒ **结论：我们没有任何「只从音频给一个 tbpm」的逻辑。** 默认自动填充 = **要新装 essentia.js**，不是复用现成的。

## 3. ★ 双窗口：大直线当时间标尺 + 只对某段采bpm

**用户口径**：大直线铺完之后**本身就能当时间标记工具** ⇒ 右上角给「**格子号（物量）↔ 毫秒**」参考；
在**分段采音**那里选**起始点**（可以是**格子**或**毫秒**）和**结束点**，
**只有这个区间内采bpm**；并且**每段可以独立选**采的音轨、**xk base**。

因为 `t = φ + k · 砖长` 是**仿射**的，格子号与毫秒**双向换算免费**。

### 3.1 ★★ 连带改动：互斥表从「全局」变成「**按区间**」

原因：如果**只有区间内采bpm**，那没开的段落**还得靠主轨采音** ⇒ **② 主轨不能全局锁死，要按段生效**。

### 3.2 更正一处（我上一条说错了）

我说过「`Segment` 已经有 `tracks` / `mode(from|until)` / `label` / `fill_gap_ms`」——
**那是老的「区间采音」结构**，不是新的 `Segment`。实际情况是**两套**：

| 机制 | 形状 | 语义 |
| --- | --- | --- |
| 老「**区间采音**」 | `{start_ms, end_ms, tracks, mode, label, fill_gap_ms}` | 显式 `[start, end]`；**有分段时被整个忽略** |
| 新「**分段**」(`core/segments.py`) | `Segment(at_ms, label, main, sub, dp, index)` + `segment_mode ∈ {from, until}` | **半开**的角色覆盖（哪几条轨当主/次/双押） |

⇒ 所以「双窗口」要落的**不是**「`Segment` 加个字段」这么简单，得先定形态（见 §7）。

## 5. 多押：角度档与「90°」

### 5.1 档位（本期口径）

```
cbpm <  300          → 15°
300 ≤ cbpm < 840     → 30°
cbpm ≥ 840：连续双押段长 < 4 → 90°
            连续双押段长 ≥ 4 → 30°
```

### 5.2 ★ 为什么判据**直接写 `cbpm ≥ 840`**，不经过 35 ms 反解

```
90° 砖的 Δt = (90/180) × 60000 / cbpm
   cbpm = 840  → Δt = 35.71 ms
   严格 Δt = 35.0 ms 反解 → cbpm = 857.1
```

⇒ 840 比「多押 ≤ 35 ms」**松 0.71 ms**。若沿用 35 ms 反解会得到 **857**，就和你给的 **840** 打架，
且会在 840~857 之间产生一个**静默翻转**。
所以：**90° 档直接以 `cbpm ≥ 840` 判**；`Δt ≤ 35 ms` 只保留给「**判定是不是多押**」。

### 5.3 拉链（travel 60）

现状**实证**（不是印象）：`core/solve.py:1461` `_tri_prefer = 60.0 if base_bpm >= 1440.0 else 120.0`
→ `figures.choose(..., prefer_travel=…)`（1514–1516）
→ `triplet_engine.plan_run(..., prefer_travel=…)`，**只在第 200 行**当**第 4 顺位排序键** `abs(T - prefer_travel)`；
前面还挡着 3 个更优先的键（`abs(log2 k)`＝不加变速 → `-y_score` → `level`）。

⇒ **它只是一个 tiebreaker，不是一套「拉链机制」**：没有触发条件、没有段判定。
⇒ **xk base 不与拉链联动**（用户口径）。

★★ **本裁定取代的旧口径（作废）**：2026-10 的「力求所有 bpm 下 Δ ≤ 25ms」。
`Δ` 一律**只当情报**上报（`dp_info` 里的 `Δ（情报）≤ …`），**不再用来选角度**。
（实测：固定表的 `90° @840` ⇒ Δ = **35.71ms**，本来就**超** 25ms 预算。）

★ **`dp_tol`（配对窗口，默认 45ms）仍然存在**，职责只有「双押轨的音 ↔ 骨架砖 怎么算同一个」。
（它是旧 UI 遗留值；要不要 45 → 35 是**另一件事**。）

★ **顺带修掉的 bug：双押落点的「扇出」**。
老判据是「**砖 → 找音**」，砖比 `2×dp_tol` 还密时**一个双押音会圈中好几块砖**：
实测 cbpm 1440（砖长 41.7ms）双押轨 146 个音 ⇒ 标成 **383** 块砖；cbpm 2880 ⇒ **638** 块。
现改成**采bpm 骨架下「音 → 找最近的那一块砖」（一对一）**并去重 ⇒ 与 cbpm 无关。
（非采bpm 路径**保持老行为**，逐字节不变，等定夺。）

### 5.6 要改的地方

`core/dp_angle.py` 现在只有两档（`CBPM_THRESHOLD = 300`、`THIN_LOW = 15`、`THIN_HIGH = 30`）
⇒ 要**加 90 档**，并且**带段长感知**（`连续双押 <4 / ≥4`），这跟 `docs/10` 的「连续 n 个 gap」是同一类判定。
