## 0. 一句话

**把「一列参数 + 四个只读视图」改成「时间轴为中心的编辑台」**：
左边**来源与段**、中间**时间轴**、右边**检查器**，底部**永远可见的报告带**；
**大直线（采bpm）单独一个可拖可缩的浮窗**，所有区域尺寸/位置**脱手即存**、下次打开复现。
参数从 68 个平铺收成 **常用 12 个常驻 + 高级折叠 + 搜索 + 预设**。
**核心是把现在三套平行区间编辑器收成一个「段（Range）」模型** —— 以后加**镜头**
只是「多一种段类型」。**并且：运镜的前置条件是「谱面走向不能锁死在 y 轴」**（见 §9）。

## 3. 病根（5 条）

1. **④ 过载**：35 个字段一屏平铺，找参数靠翻，改坏了只能凭记忆改回。用户原话：
   「**控制台的功能现在似乎多的过分了**」。
2. **三套区间编辑器是同一个东西写三遍**：`regions`（区间采音）、`segments`（分段采音）、
   `xk_ranges`（采bpm 区间）都是「时间区间 + 一组角色/属性」。三套 DOM、三个
   「在播放头加一段」按钮、三套校验。**加镜头 = 第四套。**
3. **必须看的报告埋在底部**：`#status` 是一行 200~300 字纯文本
   （`角度双押 328 处（反向 456 / 正常 0），固定写法 θ 30°×128 …, 三押 128 处 …, 走预留槽位 327 格…`），
   警告还在默认折叠的 `<details>` 里。**「跳过四押 67 处」不该要人去找。**
4. **没有撤销、没有预设、改动即重算**：开新歌要从零调 20 个参数；改了立刻重算
   （长曲几十秒），改坏了回不去。
5. **桥占固定地盘，而开源用户多半没有 BDG**；4 个视图全只读 ⇒ **改谱只能靠外部程序**。

---

## 4. 设计原则（冲突时按序）

1. **时间轴是主语**：一切「在哪段上发生什么」都在时间轴上表达；参数是补充，不是入口。
2. **一个人不需要同时看见 68 个字段**：常用 12 个常驻，其余展开/搜索/预设。
3. **不许静默**（项目铁律）：丢点、跳过四押、参数被忽略、桥没连上 —— 都在报告带上，不用点开。
4. **每一步都能回退**：参数与段的改动可撤销；重算产物可回滚到上一张谱。

### 5.1 三区职责

| 区 | 负责 | 不负责 |
| --- | --- | --- |
| **左** | 输入是谁（文件/来源/引擎）、有哪些段、有哪些轨 | 参数（在右） |
| **中** | ★ **上：视图预览**（谱面预览 / 卷帘 / 路径 / 下落式 四个页签，吃满剩余高度）；**下：时间轴带**（泳道 + 段，高度可拖，默认 ~220px）；再下：播放条 + 全曲条 | 数值属性（点段 → 右栏改） |
| **右** | 当前选中对象的**全部**属性 + 参数 | 时间编辑（在中间拖） |
| **底** | 结论与账（成功/丢/跳过/警告/时序） | 不改任何东西，纯读 |

★★ **用户 2026-10 更正（看原型截图时问的）**：「这样的东西 是拿来放轨道预览的地方吗」
⇒ 原型的中间区**只有一个铺满的时间轴画布**，泳道只占顶上几行、下面全空 —— 那是**原型的败笔**，不是设计。
正经分工：**主区 = 视图预览**（这个工具的主画面是「这张谱长什么样」）；
**时间轴只占下面一条带**，因为它的信息密度在**水平方向**（哪个段、多长），竖着 ~220px 就够，
不够可以拖大（`L.tlH`，与其它尺寸一样脱手即存）。

| 元素 | 归属 | 说明 |
| --- | --- | --- |
| 视图页签 | 主区顶部 | `★ 谱面预览`（Re_ADOJAS 三维）· `钢琴卷帘` · `谱面路径` · `4K 下落式` |
| 预览画布 | 主区，`flex:1` | 真实现场 = 内嵌 Re_ADOJAS 渲染器（现在四个都是示意图） |
| 分隔条 | 预览 ⇄ 时间轴之间 | 拖动改时间轴高度（70 ~ 视口−200） |
| 时间轴带 | 主区下方 | 段色块 + 泳道（主轨/次轨/双押/采bpm/走向/镜头）+ 播放头 |
| 播放条 · 全曲条 | 时间轴下方 | 播放/进度/音量；全曲预览（点=定位） |

★ 备选（**待你拍**）：把时间轴也做成一个 **pane**（那就也能停靠到左/右边 —— 宽屏下"时间轴放右侧"是常见布局）。

#### 5.1.1 ★★ 「时间轴有必要吗」 —— 用户 2026-10 问的，先把账算清

> 用户原话：「感觉 时间轴有必要吗 有必须它存在的考量吗」

**必须存在的只有一件事：把「时间范围」画出来 + 能改边界。**「时间轴」只是它的一种实现。
先看现在**不靠时间轴**已经能做掉多少：

| 已经有 | 能力 |
| --- | --- |
| 全曲预览条（`docs/21`） | 点=定位 · 拖动=选格 · **Shift+拖动=框选区间** · 滚轮=缩放 · 中键=平移 · 双击=全曲 |
| 区间 / 分段 / 采bpm 区间 | **列表 + 数字输入** + 「在播放头加一段」（左栏） |
| 播放条 | 播放 / 进度 / 音量 |

⇒ 「定位 + 框一段」**已经有主了**。所以时间轴真正**多出来**的只有三件事：

| # | 多出来的 | 权重 |
| --- | --- | --- |
| ① | **边界能直接拖**（不用手打数字、边听边调） | 高 —— 唯一"每天都用"的一条 |
| ② | **分层看同一时刻**（多押并发 / 采bpm 骨架 / 走向 / 镜头） | 中 —— 只有多轨道内容才需要 |
| ③ | 未来**镜头 / 走向**的段需要"在某段时间内生效"的容器 | 中 —— 等它们落地才值 |

**代价（也必须说清）**：

1. ★ **多一套轴**：payload 里已经有 3 套轴（采音轴 / `<audio>` 轴 / 谱面轴，`docs/24` §5），
   全曲条又用「格」（`docs/21`）。再来一条毫秒时间轴 = **第 4 个时间概念**，混用必出错。
2. **占屏**：220px 是白给的 —— 预览区小一圈（实测：泳道开 = 预览 562px；关 = **686px**）。
3. **代码**：多一个 canvas 绘制 + 交互 + 状态，且要和另外 3 套轴对齐。

**⇒ 三个方案（demo 里 A/C 已做成开关：`#tlbar` 上的「泳道 ✓/✗」）**：

| 方案 | 内容 | 高度 | 什么时候选 |
| --- | --- | --- | --- |
| **A（推荐）** | **带（无泳道）+ 全曲条**：带 = 段 + 标记 + 播放头，边界可拖可缩放；全曲条 = **永远看全曲的小地图**（知道自己在哪） | 96 + 54 | v0.5 默认 —— 「小地图 + 放大的编辑面」这个经典组合 |
| **B（更省）** | **只剩一条**：全曲条加高到可拖（70~150px），边界直接在它上面拖 —— **少一个组件** | ~110 | 若"永远全曲操作"够用；代价是失去"当前视窗在哪"的小地图 |
| **C** | 带 **+ 泳道**（多押 / 骨架 / 走向 / 镜头 分层） | 220 + 54 | **等镜头/走向真的落地**再开 —— 那时"分层看同一时刻"才有东西可看 |

★ 建议：**v0.5 用 A，把泳道做成开关（默认关）**，等镜头/走向落地再默认打开。

### 5.2 保留什么（不推翻已经对的）

- 左参数栏 + 右预览的**信息分工**没错，错的是**内部组织**；
- 4 个视图各有价值（谱面预览=看结果 / 卷帘=看采音 / 路径=验打结 / 下落式=验手感），
  **改成可切换、可并排（2 分屏）、跟着播放头走**；
- 轴口径三套（`docs/24` §5）、方向键=逐格、滚轮/中键语义（`docs/21`）—— **照搬不改**。

### 5.3 ★ 区域可调 + 大直线浮窗（用户口径 #2）

| 项 | 做法 |
| --- | --- |
| **三区尺寸** | 左/右栏之间、下方报告带，**拖分隔条改尺寸**（现在左栏只有 `resize: horizontal`） |
| **大直线浮窗** | 内容 = 现在的 ③b 组 + `#xk-hud` **合体**（N / tbpm / 区间列表 / 砖数 / 格子↔毫秒 / 报告） |
| 浮窗行为 | 拖标题栏移动 · 四边四角缩放 · 双击标题栏折叠成一条 · 可关闭（内容回到左栏）· **置顶于画布但不遮播放条** |
| 其它浮窗 | 同一套机制预留：`镜头`、`报告明细`、`参数搜索` 都是浮窗（同一个组件） |
| 松手即存 | **拖动/缩放结束（`pointerup`）后 debounce ~400ms 写一次**；拖动过程中不写盘 |
| 恢复 | 启动时读；**越界校验**（上次 4K、这次 1080p ⇒ 拉回可视区）；「恢复默认布局」+「导出/导入布局」 |

#### 5.3.1 ★★ **Shift+M = 布局编辑模式**（用户 2026-10 提的，原型已实现）

> 用户原话：「感觉 **设置为 按下 Shift+M 所有 ui 块都可以拖动、滚轮缩放比较好**。
> 开启移动模式之后所有 ui、…」（★ 最后半句你没写完，见 §14 #11）

| 项 | 规格 |
| --- | --- |
| **进入 / 退出** | `Shift+M` 切换；`Esc` 退出；顶栏也有 `✥ 移动模式` 按钮（**不用记快捷键**） |
| **进入后** | 所有块（左栏 / 检查器 / 报告带 / 每个浮窗）**虚线高亮** + 光标变化；顶部横幅写明状态；右下角 HUD 实时显示尺寸 |
| ★★ **内容冻结** | 用户 2026-10：「（移动模式）**不响应任何点击**」⇒ 模式内 **全 UI 停止响应**：块内控件、时间轴、全曲条、报告数字、浮窗的 `×`/`–`、顶栏所有按钮/下拉 **全部 `pointer-events:none`**；点击**穿透到块本身** ⇒ 正好变成「拖整块」；同时内容**变暗 + 去饱和**（一眼看出点不了） |

| **存盘** | 每次松手 / 滚轮停手后 debounce 400ms 写 `<userData>/ui-layout.json`（含 `zoom`） |
| **不进入模式时** | 拖动**只**走分隔条与浮窗标题栏（块本身拖不动）—— 避免正常使用时误拖（原型已按这条验收） |
| **越界** | 尺寸/位置有 min/max 夹取；启动时若窗口变小 ⇒ 拉回可视区；报告带 `0` = **自适应高度**（不是 0 高） |

★ 为什么不是「一直可拖」：正常运行时要拖**时间轴上的段**、要选文字、要滚轮缩放时间轴 ——

## 6. ★ 核心：**段（Range）模型**

### 6.1 现在三种段，本质是同一种

| 现在 | 字段 | 语义 |
| --- | --- | --- |
| 区间采音 | `regions[]` | 这段时间里**采哪些轨** |
| 分段采音 | `segments[]` | 从这点起**角色是谁**（`main / sub / dp`） |
| 采bpm 区间 | `xk_ranges[]` | 这段时间里**用哪个骨架** |
| （未来）镜头 | —— | 这段时间里**镜头怎么动** |
| （未来）走向 | —— | 这段时间里**往哪走**（见 §9） |

⇒ 统一成：

```jsonc
{ "t0": 12345.6, "t1": 45678.9,        // ms，采音轴；t1 = null ⇒ 到曲末
  "label": "高潮",
  "kind": "audio" | "skeleton" | "steer" | "camera" | "ignore",
  "props": { "tracks": [1,2], "role": "main", "n": 4, "tbpm": 250 } }
```

- **`kind` 是唯一扩展点** ⇒ 镜头/走向只是多一个枚举 + 一条泳道 + 一组字段，**框架不动**。
- 时间轴：段 = 色块（按 kind 上色），**拖边改时间**，重叠/越界即时标红。
- 左栏段列表 ⇄ 时间轴色块**双向选中**。

### 6.2 兼容纪律（不能破）

- **sidecar 一个字不改**：`regions`/`segments`/`xk_ranges` 照旧收；新前端只是
  「同一份数据的另一副面孔」，写回**只有一处**（翻译成现有字段之一），**不许前后端各存一份**。
- 老路径逐字节不变（`tests/golden/off_hashes.json` 是裁判）。

## 9. ★ 谱面走向：运镜的**前置条件**（本轮新增）

### 9.1 先给结论：**不是参数没开放，是「净转角只能是 180 的整数倍」**（已核代码 + 实测）

`core/path.py`：`heading0 = 90°`（固定）；单格净转角（无 Twirl）

```
turn_of(travel, ccw=False) = norm180(travel + 180) = travel − 180      （travel ∈ (0,360) ⇒ 不回绕）
```

⇒ 一个窗口的净转角 **`Σturn = Σtravel − 180 × 格数`**。
而时长约束 `Δt = (travel/180)·(60000/bpm)` ⇒ **同一速度档下，`W` 拍窗口的 `Σtravel = 180·W`**。
两条合起来：

```
Σturn = 180·(W − 格数)      ← W = 占几拍，格数 = 用了几块
```

**`W − 格数` 是整数 ⇒ 净转角只能是 180° 的整数倍（0 / ±180 / ±360…）。**

我把四种构造跑了一遍（`Path.from_travels`，radius=1）：

| 构造 | travels | 拍数 W | 格数 | **Σturn** | 实测 headings | 实测 points（x 变化） | 性质 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 满直线 | `[180]`×n | n | n | **0** | `90,90,90` | x 恒 = 0 | 直走 |
| **双押** | `[30,150]` | 1 | 2 | **−180** | `90→300→270` | x: 0→**1**（**再沿同一条线往回**） | ★ **折返** |
| **双押塔** | `[30,330]` | 2 | 2 | **0** | `90→300→90` | x: 0→**1**（方向不变） | ★ **侧移 +1** |
| **三押** | `[30,60,90]` | 1 | 3 | **−360** | `90→300→180→90` | x: 0→**−1**（方向不变） | ★ **侧移 −1** |

**⇒ 我们的谱面本质是一条「沿 y 轴的梯子」**：每个单元结束时 heading 要么回到 `90`、
要么翻成 `270`（折返），**永远出不了这两条线**，每单元只横向跳 ±1 格。
**这才是「方向锁死在 y 轴」的真正机制** —— 结构性的，不是开关没开。

★ 顺带解释了 `core/dp_angle.py` 里那条老观察：「正常写法 parity 不变 ⇒ 高密度时轨道
**原路重合**（实测最近距 0.000、宽度塌成 1 格）」—— 双押就是折返，折回去当然重合；
反向写法（薄格加 Twirl）把折返翻到**另一侧**，所以重叠只剩 5%~8%。**号终于对上了。**

### 9.2 要真正转向，**必须在转向的窗口里换速度档（SetSpeed）** —— 绕不开

想要 `Σturn = θ ∉ {0, ±180, …}`，必须有 `Σtravel ≠ 180·W`；
而「时长 = Σtravel/bpm」这条约束下，**只有让该窗口内的 bpm 不一样**才能既改 `Σtravel`
又保住 `W` 拍。代价（全部要进报告带，不许静默）：

1. **SetSpeed 变多**，而社区硬规则「调速要放在平格上」⇒ 与**薄格**抢位置
   （`dp_angle._setspeed_here` 会直接拒绝拆那些格）；
2. **直线率下降**、可能触发 `rules` 的回头方块 / 打结 / 重叠检查；
3. 与双押/三押**争同一格**（转向单元本身也是「一正一负两口」）。

### 9.3 ★ 走向的目标：**四方向 + 只拐直角**（用户 2026-10 更正）

> 用户原话：「其实按道理说：**不写斜线是重要的，相当重要。斜线很影响读谱**。
> 主要是目前似乎**只有上和下，很少往左和右写**。」
> ★ 随即**更正红线范围**：「**并不完全。你不能强行要求三连音和摇摆拍子硬写这种角度**」

⚠ **红线只管「走向（宏观）」，不管「格子角度（微观）」** —— 这是两回事：

| 层 | 角度由谁定 | 规则 |
| --- | --- | --- |
| **走向 / 拐角**（宏观） | 我们（走向策略） | **只用 `0/90/180/270`**（直角）。非 90° 倍数角的**整体走向** = 斜线 = 读谱灾难，**不生成** |
| **格子角度**（微观） | ★ **音乐时值** | 三连音 → `travel 120`（转角 60°）或 `60`；摇摆 → 120/60 混；…**该多少就多少，不许被强行改写** |

**为什么三连音/摇摆必须保持非 90° 倍数角**（`core/triplet_engine.py` 顶部就是这套写法）：

- 音值 `1/3` 需要**速度倍率 3**，而速度档只能是 **2 的幂** ⇒ 三连音**写不出 180° 直线**；
- ⇒ ADOFAI 里**三连音的标准长相就是 `travel=120` + `SetSpeed×2`** 的六边形
  （用户自己的 demo：`out/_triplet_demo/` 的「寻常」= `120 @ SetSpeed×2`、「拉链」= `60` 无 SetSpeed）；
- ★ 而且引擎本来就保证「**朝向回正**」（`Σ±δ ≡ 0 (mod 360)`）⇒ 三连音/摇摆
  **不会把走向带偏** ⇒ 这两条规则**根本不冲突**。

⇒ 走向要解决的是「**谱面整体往哪走**」，不是「每一格多少度」。图：

```
现在（只会上下）              目标（直角楼梯）
      ↑                          ↑ ↑ ↑
      ↑                        ┌─┘
      ↑                        └─┐
      ↑                          ↑ ↑ ↑
  一条竖线                  竖 → 横 → 竖，全是 0/90/180/270
                            （三连音段照样是它自己的 120° 六边形，不受影响）
```

**为什么现在拐不了**：生成器把每一格都硬填成 `180`（直线待遇），所以永远不拐 ——
**缺的不是机制，是「敢写 90° 格」这件事**。

### 9.4 拐角要付账（就一件事：那一格吃掉的时间）

`一格时长 = (角度/180) × (60000/速度)`。拐角格只有 90°，所以它**吃得比 180° 少一半**。
时长必须对上音乐，于是只有两条路：

| 路 | 做法 | 代价 |
| --- | --- | --- |
| **(a) 免费拐** | 把拐角**塞在音乐本来就密的地方**（音符间隔 ≈ 半拍 / 1.5 拍） | ★ **零额外代价**。单速下转 90° 的充要条件就是「那一段是半拍的奇数倍」 |
| **(b) 半速拐角格** | 那一格 `travel=90` + `速度 ×0.5` ⇒ 时长不变 | 多一处「调速落在非平格」—— ★ **但这不会比现状更糟，见下面的旧账** |

★ **旧账更正（用户 2026-10 给了完整说法 —— 我们一直读错了范围）**：

> 用户原话：「然后 对于『调速必须落在平格上』：**这个是针对于双押的，大多数时候不适用**。
> 完整的说法：**（当双押使用变速）调速必须不和旋转重叠，必须位于双押的第一格**。」

| 我们以前（写进 `docs/31` §5.2.2 / `docs/30` / `CHANGELOG`） | 用户 2026-10 更正 |
| --- | --- |
| 「SetSpeed **必须**落在 `travel=180` 平格上」（**全局**规矩） | ❌ 错。它**只针对双押**，**大多数时候不适用** |
| 「实测 47%~85% 的 SetSpeed 落在非平格 ⇒ 是一笔**待修的缺口**」 | ❌ 不是缺口，**不用修**；三连音的 `120° + SetSpeed×2` 本来就合法 |
| —— | ✅ 正确版：**（双押用变速时）调速不和旋转（Twirl）重叠 + 落在双押的「第一格」** |

推论三条：

1. 上面 §9.4 的 **(b) 半速拐角格不违规** —— 我上一条的顾虑作废（唯一硬规则仍是
   `rules.py` ①「Twirl 与 SetSpeed 不能同格」，与更正版同一条）。

- 按 §6 落成 `kind:"camera"` 段 + 一条**镜头泳道** + 检查器一组字段，导出成一串事件。
- **等你给口径**（不猜）：① 用哪个/哪些事件 + **游戏版本**；②「简单」的边界；
  ③ 要不要影响**判定**（我按纯渲染设计）。
- 顺序：**先直角走向 → 再镜头**。理由就是 §9.1：现在的谱面是一条**竖梯子**，镜头没东西可拍。

## 11. ★ 技术形态：三个选项（**唯一还没定的一条**）

## 13. 明确**不做**（v0.5 的取舍）

1. **谱面本身的可视化编辑**（拖点、改 angleData、手画图形）—— **不做**。
   定位是「从音频生成谱面」，改谱继续走 BDG/游戏编辑器。
2. **多文档 / 工程文件（.proj）**——不做（一窗一谱）。
3. **实时协作 / 云端**——不做。
4. **主题市场 / 插件系统**——不做（内部留 `kind` 扩展点就够）。
5. **移动端/窄屏适配**——不做（桌面 1080p 起）。
6. **「改时序」的转向**（牺牲对拍换方向）—— **不做**，转向一律按 §9.4 的两条路付账。
7. ★ **整体走向写成斜线**（宏观方向非 90° 倍数）—— **不做**（用户：「斜线很影响读谱，相当重要」）。
   ⚠ **但这条只管走向**：格子角度由时值定 —— 三连音的 `120°`、摇摆的 `120/60` 照写，
   **不许**为这条红线把它们改成 90° 倍数（用户 2026-10：「你不能强行要求三连音和摇摆拍子硬写这种角度」）。
