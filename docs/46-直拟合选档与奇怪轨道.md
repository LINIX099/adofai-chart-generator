# 46 · 直拟合的选档与「奇怪的轨道」（用户质疑的查证与修复）

> 用户 2026-10：「拟合之后出现了很多很奇怪的轨道。拟合逻辑中，**不适用**『最小角度』
> 这些参数吗？」

**查证结论：你猜对了 —— 而且不止「最小角度」一个。** 第一版直拟合（`docs/45`）
的选档是**一句话硬编码**，`SolveParams` 里那一堆几何参数**只用了 twirl/回正，
其余全被常量顶掉**：

| 参数（④ 里的） | 第一版直拟合 | 现在 |
|---|---|---|
| **最小角度** `travel_min` | ❌ 硬编码 20°（你设 60/90 完全没变化） | ✅ 传进 `_tier_options` |
| **直线优先** `straight_weight`（少/平衡/多） | ❌ 死参数（`speed_switch_penalty=3.0` 顶掉） | ✅ 成为「换档代价」⇒ 真的控制取舍 |
| **一档最少层数** `speed_min_run` | ❌ 完全没用 | ✅ 用「只在不掉直线率时才并档」的版本 |
| **轨道位置偏移** `use_position_track` | ❌ 完全没接（界面开着也没用） | ✅ 与 `solve()` 同一条路 |
| 选档逻辑本身 | ❌ 「粘住上一档」——16 分会粘成 **45° 发卡弯** | ✅ 复用 `solve()` 的选档 DP |
| 长休止 | ❌ 硬拆成好几个大角度格 | ✅ **1 个直线格 + Pause 事件**（等待拍，时序同样精确） |
| 精度（时序） | ✅ 一直是对的（`err_max = 0`） | ✅ 一样 |

> ★ 还有一种「参数**永远不该**在直拟合里生效」：模板 / 三连音引擎 / 自然闭合 /
> 雪花 / 音值量化 —— 它们**都要重排时间**，跟「时序优先」直接冲突。
> 现在 `report_text()` 会把这句话明说出来（免得你以为设了没生效）。

## 1. 「奇怪」到底是什么（真数据实测）

拿你那份 `Flower_Dance`（1358 点，砖长 150ms / 400bpm / 1/4 格）跑
`tools/_fit_modes.py`：

```
去噪后所有间隔都是 37.5ms 的整数倍 ⇒ r = m/4 拍 ⇒ 180·r/k
所以**角度本来就只有那么几种**（45/90/135/180/225/270/315…），
多样性是节奏本身决定的，不是拟合乱来。
```

| 配置 | 直线率 | SetSpeed | ★ 发卡弯 | 最小 travel | 时序误差 |
|---|---|---|---|---|---|
| 旧：粘住上一档 | 88.8% | **180** | 10 | 45.0° | 0 |
| DP + 直线优先「少」 | 85.3% | 93 | 27 | 22.5° | 0 |
| DP + 「平衡」（默认） | 86.6% | 98 | 19 | 22.5° | 0 |
| DP + 「多」 | **88.8%** | 132 | 16 | 22.5° | 0 |
| DP + 「多」+ 最小角度 60° | 83.6% | 106 | **4** | 67.5° | 0 |
| DP + 「多」+ 最小角度 90° | 83.8% | 112 | **5** | 90.0° | 0 |

「发卡弯」= `travel < 60°` 或 `> 300°` 的格子（画出来最刺眼的那种）。

⇒ 三件事一目了然：

1. **旧策略**（粘住上一档）把 16 分粘成 45°、32 分粘成 22.5° 的发卡弯，
   而且 **`travel_min` 改成 60/90 毫无反应**（三行数据一模一样）；
2. **DP** 会用**加速档**（k<1）把密集处铺直 —— 这正是 `SPEED_TIERS` 里那些
   `1/8, 1/4, 1/2` 存在的理由（`solve.py:74` 的原话）；
3. 想彻底去掉小角度，就把**最小角度**调大（60° 就把发卡弯从 26 压到 4）。

**现在两条策略都在**（④b 的「选档策略」）：

* **DP（默认）**＝用你的参数，密集处会加速铺直、SetSpeed 更多；
* **粘住上一档（保真）**＝尽量不动速度档，宁可留小角度。

★ 建议：拿你自己那份数据把两种各生成一次看**预览**再定 —— 这就是给你留这个开关的理由。

## 2. 两个「参数被吃掉」的真 bug（都已修）

1. **`speed_switch_penalty` 写死 3.0**：`_dp_tiers` 里 `switch_pen = straight_weight
   if speed_switch_penalty is None else speed_switch_penalty` ⇒ 界面上传的
   `straight_weight`（少 3.0 / 平衡 1.5 / 多 0.7）**永远被顶掉**。
   直拟合现在**故意**传 `None` ⇒ 「直线优先」直接控制换档代价，取舍真的会变
   （85.3% → 88.8%）。`solve()` 那条路不动（它的梯子搜索另有用法，已标定过）。
2. **`speed_min_run` 的并档把直线率吃掉**：并档会强行改写邻居的档 ⇒ 实测
   `speed_min_run=6` 时 `straight_weight` 无论 3.0/1.5/0.7/0.3，直线率全是
   83.0~83.6%（参数形同虚设）。给 `_merge_short_runs` 加了一个
   `keep_straight` 开关（**默认 False ⇒ `solve()` 逐字节不变**）：直拟合传 True
   ⇒ 并档**不许把直线格变少**。
3. 附带：长休止以前硬拆成好几个 300° 的大格；现在按 `pause_min_beats` 用
   **1 个直线格 + Pause**（Flower_Dance 上 26 处），`report` 里报
   `n_pause`，层数不变、时序照旧精确。

## 4. 还没做的（怕你觉得「参数还剩几件没接」）

* `use_pause` / `pause_min_beats` 已接（§2.3），但**没有单独的开关**：直拟合跟着
  `SolveParams.use_pause` 走（④ 里那个「长休止用 Pause」是 `solve` 组的字段，
  直拟合也读它）。
* `dp_*`（双押）走的是**后置插入**那套（`session.rebuild` 步骤 8），与 `solve`
  完全一样 —— 双押的参数在直拟合下**照样生效**。
* `target_travel / ref_quantile / band_*` 是 `solve()` 用来**推基准 BPM**的；
  直拟合的 BPM 来自去噪砖长（更准），所以那几个不参与 —— 这是设计，不是漏接。
* 真正还会「重排时间」的那些（模板/三连音/自然/雪花/量化）**故意**不接。
