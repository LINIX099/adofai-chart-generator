## 1. 先量「这份文件是什么」

### 1.1 结构（`tools/_grin_probe.py`）

```
format=1 ppqn=480 tracks=6 notes=11691 bpm0=120 len=312.9s   tempo 段数 = 1（全程 120）
trk0 Conductor  空        trk1 Piano  4924 音  ch0
trk2 Guitar     空        trk3 Bass   1255 音  ch2
trk4 Other      2372 音   trk5 Drums  3140 音  ch9（鼓）
```

**力度全是 100**、**时值全是整数 tick** —— 典型的「模型生成的 MIDI」，不是演奏录音。
（力度这一个维度在这份文件上**没有信息量**：`vel<16` 与 `vel<48` 都是 0 个音，
所以「靠力度滤碎音」在这里用不上。）

### 1.2 真砖长：**115.3846 ms**（= 520 BPM 的一拍 = **130 BPM 的十六分**）

先把整条钢琴轨做「周期 + 相位」集中度搜索（`tools/_grin_grid.py`）：

```
P=115.3846ms  R=0.7380（合并后 2335 点；原始 4924 音上是 R=0.8224）
  resid 中位 +0.12ms  p90 32.0ms  max 57.6ms   ≤5ms 48.0%  ≤10ms 70.4%
对照 P=119.79：R=0.025 · P=115.00：R=0.032 · P=120.00：R=0.016   ← 差一个量级
分 8 段各自搜：519.84 / 520.11 / 520.02 / 520.11 / 519.93 / 519.93 / 519.84 / 520.20 bpm
```

**分段周期稳定在 519.8~520.2** ⇒ 这不是巧合，是硬网格。（错周期会让分段的"最佳周期"到处乱跑。）

**外部交叉验证**：这首曲子在 osu! 的谱面页写着 **`BPM: 130.0`**
（[echosu · Grin [Expert]](https://www.echosu.com/beatmap_detail/1982581/)、
[osu! 论坛](https://osu.ppy.sh/community/forums/topics/867021)），
而 `60000/130/4 = 115.3846 ms` —— **与从 MIDI 量出来的砖长逐位吻合**。

⇒ 结论：**这份 MIDI 的"音乐网格"是 130 BPM 的十六分音符**，文件头那个 `120` 是噪声。

### 1.3 「AI 抖动」具体长什么样

合并（30 ms 去双触发）后的 2335 个音头，相邻间隔的 1 ms 直方图：

```
109ms 255 | 110ms 388 | 119ms 663 | 120ms 163
```

**不是高斯抖动，是两个尖峰**：~109.5 ms 与 ~119.5 ms（比值 1.09）。
这正是「**先按 ~10 ms 的帧率量化、再还原**」的指纹：真砖长 115.3846 不是 10 ms 的整数倍，
所以相邻间隔在 110 / 120 之间交替。

⇒ **对参数的直接后果**（这才是用户那句「把它当做需要拟合的」的实际含义）：

1. **不能用文件头的 120 BPM 当节拍**，必须用 `denoise_hint_ms = 115.3846` 把网格钉死；
2. **不能拿原始 onset 硬对拍** —— 它本身就抖 ±5 ms、极端 10 ms；
3. **要去噪/拟合**，让产物落在 **15° 的整数倍**上（= 时值落在 `砖长·k/12` 的整数格上）。

### 1.4 顺带：这份文件的钢琴轨里有一半是"同时响"

`Piano` 4924 个音里 **2589 个（52.6%）与上一个音的间隔 < 1 ms**（不同音高同 tick，即和弦），
**没有任何一个「同 tick + 同音高」的重复音**（不是模型重复触发，是真的和弦）。
所以默认 `merge_ms=30` 会把它们并成一个 onset —— 这一步是必要的，不是丢音。

## 2. 参数是怎么定的（每一步都有依据）

### 2.1 两条路先 A/B（`tools/_grin_sweep.py`）

| 路 | 直线率 | 角度词汇 | SetSpeed | 时序 |
|---|---|---|---|---|
| 直拟合 + 去噪 + 15° 阶梯 | **50.0%** | 全是 15° 倍数 | 282 | 中位 **2.72 ms** |
| 最优化 `solve()` | **0.0%** | 79.5° / 86.2° / 78.8° …（任意角） | 27 | （量化过） |

最优化那条路在这个文件上**一格 180° 都没有**：它是按「音值」推算的，而这份文件的音值
（`115.38ms / 500ms = 0.2308 拍`）**不是任何音值**，于是量化落空、参考 BPM 取到 240，
全部铺成 ~80° 的斜格。

⇒ **AI 扒的、且网格与文件头 BPM 不符的文件，只能走「去噪 + 直拟合 + 阶梯」。**
（这也正是 `docs/58`「自动贴合」给的建议：`fit_mode=direct / denoise_on / aggressive_fit`。）

### 2.2 去噪：只算网格、不挪点

`aggressive_fit=True` 时去噪**故意不挪点**（容差只花一次，交给 15° 阶梯）：

```
砖长 115.3846ms（bpm 520.000）· 相位 +19.108ms · 分母 1/4 · 格 28.8462ms
格级 R=0.270（Rayleigh z=13.02）· 拍级 R=0.738
格级残差 rms=6.886ms max=14.386ms（≤ 半格 14.423ms 才吸得对）
```

**格级 R 只有 0.27**（低于 0.30 的"认得出网格"门槛），**拍级 R 0.74**。
也就是说：**"一砖"这一级是硬网格，"十六分再往下分"那一级不是** —— 恰好对应 §1.3 的抖动指纹。
所以 `denoise_div` 用自动（1/4），拟合容差给到 50 ms（实测真正用掉的最大值 27.2 ms）。

### 2.3 角度窗口：这次新加的 `travel_max`

用户两条硬指标里，「最小 30°」本来就有 `travel_min`；「最大 270°」**之前没有**。
这次补上，做法与口径：

| 落点 | 改动 |
|---|---|
| `SolveParams.travel_max` | 新字段，**`0` = 老口径**（软上界 340 / 硬上界 358）⇒ 默认产物逐字节不变 |
| `solve._tier_options(r, tiers, travel_min, travel_max)` | 候选 `travel` 一律不得超过它；窗口比值 ≥ 9 > 2 而档位是 2 的幂 ⇒ **数学上必有一个合法档**；真取不到才退到「越界最少」并交给 `rules` 报 |
| `solve._merge_short_runs(..., travel_max=)` | 并档后的 `travel` 也守这条上界 |
| `fitdirect.snap_to_ladder(..., travel_min, travel_max)` | **阶梯吸附本身也不许把角度推出窗口**：单位数 `j ∈ [ceil(min/15), floor(max/15)]` = `[2, 18]` |
| `rules.check_chart` | 新增 `travel_above_max`（**不许静默**） |
| `sidecar.schema` + 左栏「④ 求解」 | 新增 **最大夹角** 控件（0 = 不设上界） |
| `sidecar.session.params_solve` | 透传；**同时改了激进拟合的口径**（见下） |

★ **顺带改了一个旧口径**：以前开「激进拟合」会把「最小角度」**钉死成阶梯步长 15°**，
`travel_min=90` 也会被覆盖成 15。用户既然定了「不许低于 30°」，这条就得改：

```
改前  travel_min = 15（激进模式强制）
改后  travel_min = max(15, 框里的值)      ← 15 只是阶梯**步长**，不再是下限
```

UI 那边同步：**不再把框置灰、也不再改写成 15**，只把「按 max(15, 本框) = N° 生效」写进 tooltip。

## 4. 交付时踩到的一个**假失败**（顺手修了）

导出时 `session.export()` 会拿**原始 onset**跟反解器逐层对时间。可**直拟合 + 15° 阶梯**
的设计就是**主动**把时刻挪到 15° 格子上（挪动量 ≤ 拟合容差）—— 于是：

```
改前  [FAIL] 对照 2335 层  最大误差 37900.6 us  首个超差: floor#1 got=115.385ms exp=109.375ms
改后  [OK]   对照 2335 层  最大误差 0.1 us
      ★ 直拟合 15° 阶梯**主动**改了时刻：最大 27.16ms（≤ 拟合容差）——上面这条是**序列化**校验
```

**修法**：直拟合 + 阶梯开着时，序列化校验改拿**拟合后的时刻**（= 谱面模型自己的时刻，
即 `times_from_chart`）比，另起一行把「相对原始 onset 挪了多少」如实报出来。
「拿原始 onset 硬比」是**保真读数**，不是**写盘正确性**，两者不该混成一条红字。

### 7.2 三条可以带走的结论

1. **放宽角度窗口（30/270 → 15/340）只省 2 次 SetSpeed（282→280）。**
   因为这份文件里「必须用 >270° 才能省掉一次换档」的地方只有 **17 格**。
   —— **你想给的角度自由度，不是这里的瓶颈。**
2. **真正的杠杆是「换一档的代价」**（`直线优先` 那一档同时当换档代价用，见 `core/fitdirect.pick_tiers_dp`）：
   `平衡`(1.5) → `少`(3.0) ⇒ **SetSpeed 282 → 196（−30%）**，
   **角度窗口与 15° 阶梯一字不动**，直线率只从 50.0% 掉到 45.7%。
   这是**几乎免费**的省法。
3. **放弃 15° 阶梯、改用「时间绝对吸附」**（`denoise_div` 控制吸附粒度）是另一条：
   - `div=12`（步长 9.615ms）：角度词汇 15 → **28 种**，SetSpeed → 263，
     而**时间偏差反而从 `max 27.16ms` 降到 `7.13ms`** —— 因为绝对吸附的偏差上界
     就是半格（4.8ms），不会像「逐点重锚」那样偶尔走远。
   - **关掉 Pause**（`use_pause=False`）后：**SetSpeed 178 · Pause 0 · 事件合计 178（−42%）**，
     偏差仍是 2.48 / 7.13ms。
   - 代价：直线率 50% → 39%，角度有 12.8% 不在 15° 档上，**自重叠对数 801 → 1522**
     （少换档 ⇒ 同样的档位铺更长 ⇒ 闭合图形更多、更容易叠在一起）。

### 7.3 交付

两档已导出（都在 `out\_grin\export\`，序列化反解都是 **0.0 µs**）：

|---|---|---|

## 12. ★ 修的 bug：「激进策略」在这份 AI MIDI 上跑不通（2026-10 用户报）

> 用户原话：「ai 的 midi 好像不能用激进策略采音喵，好像跑不通喵」
> →「准确的来说，好像是**拟合时激进策略不通**喵」

三个各自独立的缺陷，全在 `travel_max`（本次新加的最大夹角）这条线上，**三处都实测复现**：

### 12.1 ★★ `core/ladder.py`（「使用激进的采音策略」）**完全不认最大夹角**

* `rung_ok()` 把上界**写死 345**，`p.travel_max` 整个阶梯一次都没读过；
  第 2/3/4 级全都走这个闸 ⇒ 闸形同虚设。
* 更糟的是 `solve_aggressive()` 写 meta 时**只写了 `travel_min`** ——
  而 `core.rules` 的 ③c「最大夹角」读的是 `meta["travel_max"]`，
  读不到就当「没设上界」⇒ **状态栏写着「违规 0」，谱面却满是超窗的格子**。

实测（`out/_grin/grin.mid`，`travel_max=270`，`aggressive_pick=True`）：

| | 修前 | 修后 |
|---|---|---|
| 最高 travel | **345.00°**（338.25 / 331.5 / 345 共 **10 格** >270） | **255.75°**（超窗 0） |
| `meta["travel_max"]` | `None`（检查器瞎） | `270.0` |
| 状态栏违规 | 0（假的） | 0（真的） |

修复：
* `core/ladder.travel_hi(p)` = `max(15, min(345, travel_max||345))`，`rung_ok` 用它；
  **`exempt`（双押/雪花）只豁免「最小角度」**，上界照样卡
  （③c 只对双押格开口子、雪花段照查，两边口径对齐）。
* `solve_aggressive` 补写 `meta["travel_max"]`。
* `core/figures.py`：`nat_candidates` 的上界从 `natural_travel_max` 改成
  `min(natural_travel_max, travel_max)`；`eng_candidates`（三连音引擎）也加上界
  （以前它俩都不受用户窗口管）。`travel_max=0` 时 `min()` 取回原值 ⇒ **老路径不动**。
* 第 1 级**手写模板段刻意整段照抄**（`docs/25` §5「具体写法优先」），不强行改它 ——
  但它越界时必须被 `core.rules` 报出来（现在 meta 有值了，报得出来）。

### 12.2 ★ 直拟合下勾「使用激进的采音策略」= **静默失效**

`aggressive_pick` 是 `core.ladder` 那条路，`solve()` 里那行早退**只有最优化会走**。
在直拟合下勾它，以前**一个字都不说**，产物与不勾**逐字节相同**
（实测 sha1 都是 `5667b07c8648`）—— 看起来就是「坏了」。

修复：`sidecar/session.py` 在 `fit_mode=direct` 且 `aggressive_pick` 时上屏
「这次**没用上**，要它请切回最优化」；`app.js applyFitLock()` 同期把它**置灰**并写明原因
（与「激进拟合」那把锁对称）。最优化下照旧可点。

### 12.3 ★ 去噪的账在激进模式下**报错了数**

激进模式下 `rad` 是**故意**的 0（去噪只算网格、挪点交给 15° 阶梯），
但警告照打 `rad`，于是用户设了 50ms 却看到
「拟合容差 **0.0ms**：2335 个点离格超过它，**原样保留**（想全吸就把容差调大）」——
读了会以为激进根本没生效，而且**照着它调容差永远没用**（挪点的是阶梯）。

修复：激进模式下改成说清「去噪故意一个点都没挪，容差 Nms 整个交给 15° 阶梯，
下面那条『修正 N 音』才是账」；只有非激进模式才打原来那句。

### 12.4 顺带：`travel_max < 180°` 是**定义冲突**，现在明说

直线格（一砖一音）与 Pause 格按定义就是 180°，所以上界 < 180° 根本满足不了。
以前**静默照吐**。现在 `sidecar` 上屏警告（照常出谱，但不装作满足）。
