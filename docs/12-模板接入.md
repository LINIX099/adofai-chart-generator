# 12 · 模板接入（主体路径）

## 流水线

```
patterns/*.adofai（权威）
        │  tools/extract_templates.py
        ▼
patterns/templates.json          ← 15 个模板
        │  core/templates.py  load() / match()
        ▼
core/solve.py::solve()           ← 模板优先，DP 兜底
        │
        ▼
.out/<曲名>/main.adofai
```

## 模板结构

```json
{"id": "几种三角形_4", "name": "直角三角形 前16后8",
 "notes": [0.25, 0.25, 0.5],      ← 身份（单位：四分音符拍数）
 "travel": [45, 45, 90],          ← 落地角度（= notes × 180，speed 1）
 "twirl": [false, false, false],
 "pos": [], "rounds": 1, "beats": 1.0, "tags": "快快慢"}
```

## 抽取结果（`patterns/templates.json`，15 个）

| 来源 | 模板 |
|---|---|
| A 均分骨架 | 八分×2 `90·90`、十六分×4 `45·45·45·45` |
| B 强弱拍 | B1 `270·90`、B2 `90·270`、C1 `90·180`、C2 `180·90`、C3 `270·180`、C4 `180·270` |
| C 摇摆拍子 | D1 `135·45`、D2 `45·135` |
| **几种三角形** | `60·60·60`、`90·60·30`、`90·30·60`、`45·45·90`、`90·45·45` |

> `A1 四分（直线）`被跳过：它整段都是 180°，属于「空」间隔，直线由 DP 直接给。

## 匹配规则（`core/templates.py::match`）

1. **贪婪最长优先**，区间不重叠
2. **轮数叠加**（用户口径）：同模板能接着重复就重复，返回 `reps`
3. **时序闸** ⭐：模板会把该格时长锁成「音值 × 拍」，所以只在实际 Δt 离它
   ≤ `template_timing_tol_ms`（默认 0.5ms）时才用

> 判定用**量化后**的音值（节奏型身份），时序闸看**原始**音值。

## ⚠️ 踩过的两个坑

### 1. 按原始毫秒匹配 → 命中率极低
`rs` 是从 `t_ms` 算的，混着 tempo/浮点噪声，直接和模板的整数音值比基本不中。
改成用量化后的 `beats` 折算到本谱基准（`rq = qbeats × base_bpm / midi_bpm`）才正常。

### 2. 不加时序闸 → 时序崩 81ms
模板把时长锁成模板音值，但实际 Δt 可能没量化干净。
`Automaton_Waltz / 少`：364.9ms 被当成 1 拍 = 324.3ms，差 40.5ms，累积后
`check_offset` 报 **80982µs**。加时序闸后 → **173µs** ✓

## 两种模式（`SolveParams.template_only_nonstraight`）

| 模式 | 含义 |
|---|---|
| `False`（模板-全） | 能匹配就套，连 DP 本来是直线的地方也换 |
| `True`（默认，模板-修） | 只在 DP 会给出**非直线**的地方套，保住「直线为主」 |

实测（`tools/compare_tpl_modes.py`）：

| 样本 / 预设 | DP 直线 | 模板-全 | 模板-修 |
|---|---|---|---|
| Automaton_Waltz / 少 | 53.4% | **27.7%**（581 格） | 53.5%（355 格） |
| Automaton_Waltz / 平衡 | 78.4% | 78.4%（56 格） | 78.4%（56 格） |
| FallenEra / 少 | 57.3% | **22.3%**（462 格） | 56.3%（270 格） |
| FallenEra / 平衡 | 65.7% | 60.2%（38 格） | 65.7%（**0 格**） |
| MemoryLocked / 平衡 | 54.4% | 54.4%（8 格） | 54.4%（8 格） |

**冲突：模板会把直线换掉。**「少」预设下模板-全把直线从 53% 压到 28%，
和用户「一张谱面应该直线为主」的红线打架，所以默认用「模板-修」。

## 段落时长规矩（用户口径）

> 「检索一段时间内的音符数量，做一个阈值来决定这里用速度×2还是 90°，
> 一般比较短的段落就 90°（适用于 <10s）」

实现：`SolveParams.template_max_span_s`（默认 10s）+ `template_rest_ms`（段落怎么切）。

**⚠️ 关键在「段落怎么切」。** 实测（`tools/passage_stats.py`）：

| 样本 | 休止阈值 200-300ms | | 休止阈值 1s | |
|---|---|---|---|---|
| | 段落数 | >10s 占时长 | 段落数 | >10s 占时长 |
| Automaton_Waltz | 299 | 12% | 6 | **94%** |
| FallenEra | 232 | 28% | 8 | **85%** |
| MemoryLocked | 138 | 64% | 10 | **84%** |

- **休止阈值 200~300ms（乐句级）** → 大部分时间落在「短段落」，模板照常工作
- **休止阈值 ≥1s** → 段落合并成 2~6 个长段，>10s 占 84~94%，
  **模板几乎被完全关掉**（Automaton 56→4 格、MemoryLocked 8→0 格）

所以默认取 **300ms**（乐句级），只有真正连续 >10s 的长流才交回 DP 用速度×2。

# 13 · 速度事件与长休止（用户两条口径）

## 13.1 用户口径

> 「目前程序还是倾向于用 set 速度来制谱。人类的谱面不会出现如此大量的 set 速度
> （除非 magic 形状，这个我后面细说）。如果音乐长时间没有声音，
> 就让程序使用**暂停节拍**，不要尝试硬对音让轨道扭得奇奇怪怪的。」

## 13.2 ⭐ 标尺：真谱的 SetSpeed 密度（`tools/bench_setspeed.py`）

| 语料 | 谱数 | 格数 | SetSpeed 合计 | **每 100 格** | 完全没用的谱 |
|---|---|---|---|---|---|
| **★ EX 权威** | 9 | 4 365 | 59 | **1.35** | 22% |
| 主语料（社区） | 231 | 608 426 | 39 795 | 6.54 | 3% |
| **我们的输出** | | | | | |
| Automaton_Waltz | 1 | 850 | 92 | **10.8** | — |
| FallenEra | 1 | 566 | 31 | 5.5 | — |
| MemoryLocked | 1 | 196 | 21 | **10.7** | — |

**结论：我们比 EX 脏 4~8 倍，比社区脏谱还脏。** 用户说得对。

EX 的 Pause 密度：每张谱 0.44 个（很少用，但确实用）。

## 13.3 为什么会有这么多 SetSpeed

DP 的目标是 `Σ(直线 − 速度代价) − λ·Σ(换档)`。
为了让某一格变成 180° 直线，DP 会去调 `k`（`travel = 180×rs/k`）——
**每个音值都对应一个能让它变直线的 k，所以音值一变，k 就跟着变** → 到处 SetSpeed。

再加两个来源：
1. **模板段强制 `k=1`**：一段模板进出各一次换档（23 段 ≈ 46 个事件）
2. **Pause 格强制 `k=1`**：同理

实测：把换档罚从 3 拉到 1e9，Automaton_Waltz 仍然有 58 个事件（≈ 模板段 46 + Pause 12），
而**直线从 60% 崩到 20.6%** —— 说明「直线为主」和「少 SetSpeed」在这个目标函数下是**互相打架**的。

### 根因：`choose_reference` 故意选「靠换档换直线」的基准

它按 `(直线 − λ·换档, 直线, −换档, …)` 排序，λ（`straight_weight`）默认 1.5，
于是「多换几次档、多换些直线」总是划算。

而 **EX 谱的写法是：把基准 BPM 定成「主音值 = 一拍」，主音值直接就是直线，
其它音值自然给出 90°/135°/270°，几乎不用换档。** 这正好也是「45° 整数倍角度」世界。

→ **要贴近人类，应该把 λ（换档代价）提到远大于「一条直线」的收益**，
或者干脆改成「先定基准使主音值 = 直线，再只在必要时换档」。

## 13.4 长休止 → Pause（已实现）

`SolveParams.use_pause`（默认 True）+ `pause_min_beats`：

```
间隔 > pause_min_beats 拍  →  这一格走一条直线（travel = 180°，1 拍），剩下的时间全交给 Pause
pause_beats = r − 1（退回 k=1 时）/ r/k − 1（沿用前一档且仍留下 ≥0.25 拍时）
```

> ★ **2026-10 口径变更**：默认从 **4 拍** 改成 **1 拍**（= 只要比一拍长就用暂停节拍，
> 而不是让行星减速爬过去），并修掉「沿用前一格速度档导致 `pb = r/k − 1` 恰好为 0、
> 等待悄悄变回缓速」的坑。实测 Automaton 直线率 49.7%→70.1%、时序 167us→45us。
> UI 参数标签也从「Pause 阈值」改成「等待拍阈值」。详见 `docs/24` §2。

效果（MemoryLocked 两个巨大休止）：

| 休止 | 修复前 | 修复后 |
|---|---|---|
| 67 800 ms | travel **158.9°**（k=512 爬行格） | **travel 180° + Pause 451 拍** |
| 56 400 ms | travel **132.2°**（k=256 爬行格） | **travel 180° + Pause 375 拍** |

`times_from_chart` 已改成 `(travel/180 + pause_beats) × 拍`，时序误差仍是 0~143µs。
`core/writer.py` 输出：
```json
{"floor": f, "eventType": "Pause", "duration": 451.0,
 "countdownTicks": -1, "angleCorrectionDir": -1}
```

> ⚠️ Pause 阈值别调太低：设成 2 拍时，Automaton_Waltz 的 SetSpeed 从 92 涨到 157
> ——因为每个 Pause 格都强制 k=1，进出一个来回就是 2 个事件。

## 13.5 速度档最短段长（`speed_min_run`，默认 6）

`_merge_short_runs`：一个速度档连续用不到 6 层就并给邻居
（前提：并完 travel 仍在 [15°, 345°]，不会变回头方块）。

效果有限：Automaton_Waltz 92 → 74。因为**大头是模板段和 Pause 格强制 k=1**，不是 DP 选出来的。

## 13.6 待用户定

「直线为主」和「少 SetSpeed」在这个目标函数下互斥。两条路：

- **(a) 贴近 EX**：把换档代价提到极高 / 改成「主音值 = 直线」定基准。
  结果大约 Automaton_Waltz 直线 20%、SetSpeed 58 个。**但 20% 直线破了 45% 红线。**
- **(b) 保直线**：现状。直线 60%，SetSpeed 74 个（EX 的 5.5 倍）。
- **(c) 中间**：换档罚 10 左右。

# 14 · 多音轨采音（用户提议的取巧解法）

## 14.1 用户原话

> 「我想到一个取巧的解法，我们先把**多音轨采音**做出来，从这一层上**减少空白音的位置**试试。
> 先不做双押，双押待会再说方案。」

## 14.2 为什么这是对的

原来的管线只挑**一条轨**（`auto` = 第一条非鼓轨），别的声部的音全丢，
那些位置就成了「空白音」——求解器为了填时间只能扭轨道（或者塞 SetSpeed、长 Pause）。

采音层本来就是这个结构：`build_onsets(notes, params)` 只吃一个音符列表。
**所以多轨 = 把几条轨的音符合起来再走同一套「同时音合并」**，改动很小：

```python
onsets_mod.select_tracks(m, "all")          # auto / all / all+drums
onsets_mod.build_onsets_multi(trks, params)
```

## 14.7 ⭐ 用户：「全采又太奇怪了」→ 改成「主轨 + 补空白」

> ⚠ **本节记录的是当时的决策，机制已在 `docs/23` 退役**：用户后来要求
> 「主轨也可以选不止一条，哪条有音采哪条」，于是改成**主轨多选 + 取并集**，
> `scope` / `primary_mode` / `fill_gap_ms` 三个字段连同 `build_onsets_fill` 的
> 调用路径一起删掉了（函数本身保留给 `tools/`）。下面的实测数据仍有参考价值
> ——它证明了「全采」在直线率上不划算，这也是为什么**默认依旧只勾一条主轨**。

**用户原话**：「但是 全采又太奇怪了。可以不强制全采音吗？或者允许做一些采音取舍？你怎么看」

「全采」的问题：把伴奏、内声部一起采进来，**那已经不是任何一条音乐线了**，
形状会很怪（FallenEra 直线掉到 35%，破红线）。

用户最初的说法其实一直是「**减少空白音的位置**」——不是全采，是**补空白**。
所以实现 `onsets.notes_fill_gaps()`：

```
主轨不变 → 只统计主轨的空白（Δt > gap_ms）→ 只在那些窗口里从其它轨补音
```

| | 全采 | 957 | 0 | 61 | 72.6% |

**结论：补空白同时拿到「空白归零」和「保住直线为主 45% 红线」。全采保不住。**

### 取舍旋钮

| 旋钮 | 在哪里 | 作用 |
|---|---|---|
| **采音范围** | ② | 主轨+补空白 / 单轨 / 全采 |
| **补空白阈值** | ③ | 主轨空白超过多少 ms 才去补。调小=更像全采，调大=更像单轨，0=全并 |
| **主轨** | ② 光标 | 光标选哪条，主轨就是哪条 |
| **补哪些轨** | ② 勾选框 | 补空白只从**勾选的**其它轨里取音 |

| | **trk1 钢琴 均高58.2 力度75.6** | 676 | **0.30** | **97.9%** |
| FallenEra | trk0 钢琴1 均高80.0 力度101.2 | 766 | 2.35 | 47.8% |
| | **trk2 钢琴2 均高72.9 力度80.8** | 1116 | **0.36** | 60.2% |
| MemoryLocked | trk0 小提琴 均高78.6 力度115.8 | 1277 | 4.46 | 66.2% |
| | trk1 钢琴1 均高77.0 | 1689 | 10.53 | 72.7% |
| | **trk2 钢琴1 均高52.6** | 1744 | **21.09** ← 灾难 | 94.5% |
| | trk4 钢琴2 均高67.9（320 音） | 320 | 0.00 | 60.3% |

**各启发式会选谁：**

| 启发式 | Automaton | FallenEra | MemoryLocked | 评价 |
|---|---|---|---|---|
| 音符最多 | trk1 | trk1 | trk2 | **最差**（MemoryLocked 挑到低音伴奏，21/100） |
| 平均音高最高 | trk0 | trk0 | trk0 | 三首样本都挑到旋律轨 ✓ |
| 平均力度最大 | trk0 | trk0 | trk0 | 同上 ✓ |
| 最贴 EX 标尺 | trk1 | trk1 | trk4 | 统计最干净，但**未必是音乐上对的那条** |

### 结论

1. **「音符最多」不能当主轨启发式** —— 它总是挑到最密的伴奏/低音。
2. **默认改成「平均音高最高」**（旋律通常在最上面），三首样本都对。
3. **自动只是起点**。统计干净 ≠ 音乐对：MemoryLocked 的 trk4 只有 320 个音，
   统计上最贴 EX（0.00/100），但它基本没在响，当主轨就是空的。
   **最终还是要靠光标手动点着试**，哪条音乐线听着对就用哪条。
