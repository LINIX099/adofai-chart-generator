# 59 · 镜头与轨道颜色调度（设计定稿）

> 用户口径（本轮原话）：
> 1. 「镜头与轨道颜色调度」；「轨道配色调度**是有固定公式的**，镜头差不多也有」
> 2. 镜头：「无论现在实际轨道朝向，永远让屏幕上的直线和电脑屏幕的两条窄边夹角为 90 度」
>    → 澄清后 = **拐角时间内不动，出拐角后回正到左右走**；「所有镜头操作都是缓动」
> 3. 「90 度拐角不动 / 三连音和所有预设图形不动 / 雪花公式动 / 别的 = 全动」（主语 = **镜头的旋转**）
> 4. 颜色：「**只改轨道颜色**」；「**只有换手押给换色**」；「固定用白色 + 黑色的霓虹方块」
> 5. 换手押定义：**X = 双押，O = 普通格，满足 `OOX` 循环（周期 3 个事件）的结构就是换手押**；
>    X = **双押整组（2 格）**，O = **单格**；**连续 ≥ 2 个周期**才算；**不看 Twirl**
> 6. 染色范围 = **只染那一格**（不是染到下一个换手押）；颜色 = **统一黑底白边**；
>    常规格 **不动**
> 7. 默认 **开**、可关；**这一轮只落地颜色那半**，镜头那半实现排后

---

## 0. 一句话

给谱面自动生成两类**渲染事件**写进 `.adofai` 的 `actions`：
**换手押上色**（本轮落地）与**镜头调度**（本轮出设计、排后实现）。
两者都**只写事件、不碰 `angleData` / `bpm` / `travel` / `Twirl`** ⇒ 时序零影响。

## 1. 事实基线（全部实测，不是猜的）

### 1.1 事件名：v19 没有 `SetTrackColors`

| 事件 | 实测字段（社区语料 108 份 + 你 535 份谱面） |
|---|---|
| **`RecolorTrack`** | `floor, startTile, endTile, gapLength, duration, ease, trackColorType, trackColor, secondaryTrackColor, trackColorAnimDuration, trackColorPulse, trackPulseLength, trackStyle, trackGlowIntensity, angleOffset, eventTag` |
| **`MoveCamera`** | `floor, duration, relativeTo, position, rotation, zoom, angleOffset, ease, eventTag`（`active / dontDisable / minVfxOnly` 为可选） |

- `RecolorTrack` 的 `trackColorType` 实测取值：`Single / Glow / Stripes / Blink / Switch / Rainbow / Volume`
- `trackStyle`：`Standard / Neon / NeonLight / Basic / Minimal / Gems`
- `MoveCamera.relativeTo`：`Player / Tile / Global / LastPosition / LastPositionNoRotation`
- ★ **`MoveCamera` 不写 `relativeTo` = 继承上一条已用模式**（`vendor/Re_ADOJAS/src/lib/Player/CameraController.ts:463-464`）。
  读语料时不还原因果会全错（MM2 的 1206 条绝大多数不写）。

### 1.1 事件选型：**`ColorTrack` + `justThisTile`**（不是 `RecolorTrack`）

> ★★ 这一条是**用户两次进游戏实测**逼出来的，是本轮最重要的结论，别再退回 `RecolorTrack`。
>
> 1. 第一版我选了 `RecolorTrack`（编辑器里叫「**重新设置**轨道颜色」），
>    用户实测：「我期望他是『**设置**轨道颜色』而不是『**重新设置**轨道颜色』，
>    后者必须是**走过后才展示，起不到提示作用**。」
> 2. 我当时的补救是「把事件**提前到曲首**发」——用户又拿**编辑器截图**问：
>    「假如一个谱子里面几百个换手，你准备全放第一个格子吗？你确定吗」（编辑器里会显示「1/500」），
>    并让我「**去游戏源码里找找『仅作用于当前方块』的事件**」。

**游戏源码里的答案**（`‹游戏反编译源码目录›\`）：

| 事件 | 编辑器名 | 语义 | 结论 |
|---|---|---|---|
| `RecolorTrack` | **重新设置**轨道颜色 | **运行时**：玩家时间越过事件所在格，才把 `startTile..endTile` 范围扫着翻色（`vendor/Re_ADOJAS/.../TileColorManager.ts:542-569`） | ✗ 走过后才展示；要靠「提前发」硬凑，还会堆叠 |
| **`ColorTrack`** | **设置**轨道颜色 | **建关时逐格预演**，颜色直接写进那一格的组件（`scnGame.cs:379-461`、`:653 orAddComponent.color1 = tempColor1`） | ✓ 那格**一出生就是该色** |

而「**仅作用于当前方块**」= `ColorTrack` 的 **一个字段 `justThisTile`**（`scnGame.cs:447-461`）：

```csharp
item5.TryGet<bool>("justThisTile", out var output6);   // 本格读一次
...
if (!output6)                    // 只有【不】justThisTile 才写回「全局当前颜色」
{
    color1 = tempColor1;         //   ⇒ justThisTile:true ⇒ 只改这一格，下一格自动恢复
    style  = tempStyle;
    startOfColorChange = tempStartOfColorChange;
    ...
}
```

编辑器自己也是这么用的：`scnEditor.PasteTrackColorSingleTile()`（「单格粘贴」）
原本还要在 `id+1` **补一条恢复事件**；有了 `justThisTile` 就**不用补**了。

**语料核对**（`build/_find_colortrack.py`，全量重扫，纠正我上一轮的观测盲区 ——
上一轮我的扫描器只统计 `INTEREST` 里列的事件，而 `ColorTrack` **不在那张表里**）：

- `ColorTrack` 在真实谱面里**用了几千次**（`floor` 有 **3898** 种不同取值，
  单份最多 **1291** 条，例：`drive-download-…\level.adofai`）；
- 字段真值（8 种组合，最全的一种）：
  `floor, eventType, justThisTile, trackColor, secondaryTrackColor, trackColorType,
   trackColorAnimDuration, trackColorPulse, trackPulseLength, trackStyle,
   trackTexture, trackTextureScale, trackGlowIntensity`（`floorIconOutlines` 可选）
- `justThisTile`：`['False', 'True']` 两种都真实存在 —— 我们要的是 `True`。

### 1.2 时间口径（两边一致，已对账）

```
travel    = 180 − |ΔangleData|          # 180 = 直线
duration  = travel / 180 × 60000 / bpm
```
- 权威实现：`vendor/Re_ADOJAS/src/lib/Player/levelLoaderWorker.ts:130-135`
- 我们这边：`core/path.py:67` `turn = 180 − travel` … `angleData = 90 − heading`
- 实机语料：`samples\三种三连音写法.adofai` 的 `angleData` 与逐格耗时自洽

### 1.3 「锁朝向」的机制（镜头那一半的基石）

`PLUM MEGAMIX`（MM1 正本，v5，9452 格，177 条镜头）**全曲 100%** 是
`relativeTo:"Player"` + `position:[0,0]` + `rotation:0`（只动 `zoom`）。
`relativeTo:"Player"` 把相机挂到行星坐标系上 ⇒ 玩家朝向在屏幕上被钉死
⇒ **「直线永远左右走」= 这一条 + 一个 90° 常量**，不需要逐格算绝对角度。

### 1.4 语料里「黑底白边」怎么写的

全语料 `RecolorTrack` 共 **32366** 条，其中「一黑一白」**8585** 条：

| trackColorType | trackStyle | 条数 |
|---|---|---|
| Single | Minimal | 5308 |
| Single | Standard | 3079 |
| Glow | Basic | 83 |
| Single | NeonLight | 60 |
| Single | Neon | 20 |

用户拍板要的是 **`Glow` + 主 `000000` + 副 `ffffff` + `Neon`**（此组合本身在语料里很主流：
`(Glow, Neon)` 出现 6226 次，全语料第 2 多）。

### 1.5 换手押样例（`out\换手双押交互.adofai`，用户亲手写的）

- `bpm=250`，floor 1 有 `SetSpeed{Multiplier, ×4}` ⇒ 之后 **1000 BPM**（**人按不出来，这是机制演示谱**）
- 82 格；8 格一循环 `0,150,180,180,180,30,0,0`
- 逐格 `travel`：只有三种 —— **`180°`(42 格·60ms) / `150°`(20 格·50ms) / `30°`(20 格·10ms)**
- 双押对 = `[travel 30°, travel 150°]`（两格和 180° = 我们项目里 `[θ, 180−θ]` 的写法，θ=30）
- 双押对的起点间距 **4 格**，即两个双押之间正好 **2 个普通格** ⇒ `X O O` 循环 ✓
- 19 个 Twirl **全部**压在双押的薄格上，且进入方向 `−150/+150` **交替**
- 几何：`3 格直下 → 发卡急转 → 1 格回斜 → 3 格直上 → 反向发卡`的往复锯齿
  （ASCII 轨迹见 `out\_handswitch.txt` 尾部）

### 1.6 镜头反推结论（MM1 4892 重制版 / MM2 v18）

四种元件，语料反复出现：

| # | 元件 | 实测原话 |
|---|---|---|
| 1 | 锁朝向 | `rel=Player, pos=[0,0], rotation=0` |
| 2 | 摆头 | `rot=+14 dur=12 InBack` → `rot=0 dur=12 OutBack`；小号 `±5 dur=8 OutCirc / 0 dur=8 InCirc`；再小 `±3 dur=0.5 OutQuad` |
| 3 | 缩放呼吸 | `zoom 250 → 140/125/50/25/1`（`InBack/InCirc/InExpo`）→ `250`（`OutSine/OutExpo`），4~12 拍；重音处 `dur=0` 砸到 `zoom=1~25` 再弹回 |
| 4 | 大转 | 只落在**长旋转图形的起点**。短：`rel=Player, rot=±90/±180/±360/720, dur=0~12`；长：`rel=LastPosition`（从当前相机角累加）或 `LastPositionNoRotation`，实测 `rot=-90 dur=96`、`rot=540 dur=64`、`rot=720 dur=48`，同时 `zoom 1↔500` |

**已证伪的猜测**（我自己先前编的，写在这里防止再犯）：
- ✗ `duration = 图形长度` —— 图形实测 1.17~1.5 拍，镜头 `duration=9.333` 拍；
- ✗ 「图形转多少镜头转多少」—— 图形总转角（+240/+450/+720°）与镜头 rotation（±14/±32/±90）**无数值对应**；
- ✗ 「换手押 = Twirl」—— MM1 里换色落点与 Twirl 同格只有 19.8%。

## 2. 颜色调度规范（本轮落地）

### 2.1 换手押判据

设 `dp(i)` = 第 i 个「双押组」（两格 `[θ, 180−θ]`，θ 由现有双押逻辑决定），
`G(i)` = 第 i 组与第 i+1 组之间夹的**普通格**数量。

```
换手押段  ⇔  存在连续 ≥ 2 个双押组，使  G(i) == 2  （对段内每一对相邻组都成立）
```

- 周期换算：`O O X O O X`（单位 = 事件：X = 双押组 2 格，O = 单格）⇒ 每组占 **4 格**
- **最小长度 = 2 个周期**（即 ≥2 个双押组、中间隔 2 格）；孤立的单个双押**不算**
- **不看 Twirl**（判据纯几何；但生成侧仍会照常写 Twirl，那是另一套逻辑）
  ★ 用户样例支持这条：20 个薄格里**只有 19 个带 Twirl**（floor 1 那个薄格没有 Twirl），
  结构却完全规整 ⇒ 拿 Twirl 当必要条件反而会漏。

#### 2.1.1 ★★ 只染「换的那个格子」（用户 2026-10 的记号串）

> 用户原话：「哦对，**换手的意义在于：只在换的那个格子进行染色**。我用 D 标注染色的双押
> `XOODOOXOODOO`」

即：**X = 双押、O = 普通格、D = 被染色的那个双押**，而 D 不是每一个 X：

```
X O O D O O X O O D O O …      ← 每 2 个双押才染 1 个（从链内第 2 个起算）
```

对应两个参数：

| 参数 | 默认 | 含义 |
|---|---|---|
| `handswitch_color_every` | **2** | 每隔几个双押染一个（`1` = 全染，那就不叫「只在换的那个格子」了） |
| `handswitch_color_phase` | **2** | 从链内**第几个**双押开始染（1 起算）；用户记号串 ⇒ **第 2 个** |

⚠ 链比相位还短时（例如 `min_cycles=1` 的孤立双押链 + `phase=2`）**一条都不染**，
且**必须报出来**（`skipped_why`），不许静默。

#### 2.1.2 双押组怎么认（两条输入路径）

| 输入 | 认法 |
|---|---|
| **我们自己生成的谱面** | 用 `ch.meta["dp_pairs"]` —— `core.dp_angle.apply` 回填的**权威**记录（`(薄格, 薄格, 剩余格)`，每块薄格一条；同一剩余格两块薄格 = 三押）。`core.dp_midspin` 是另一种编码，同样从 `dp_pairs` 认 |
| **外来谱面 / 纯几何** | 扫相邻两格：`travel[i] + travel[i+1] == 180` 且两者都不是直线（`180`）。⚠ `(90°, 90°)` 与**普通直角折角**在几何上完全一样 ⇒ 我们**只接受 `min(travel) < 90°` 的组**，把 `(90,90)` 候选**逐条报出来**（`n_skipped_ambig`）。有 `dp_pairs` 时不存在这个歧义（90° 的双押照样认） |

样例实测：几何判据在用户样例上给出 **20 个双押组、travel 恒 `(30°, 150°)`、
组间恒 2 格、无假阳性**（`tests/test_colorize.py` A 组守这条）。

### 2.2 染色写法（★ **`ColorTrack` + `justThisTile`**）

在**每个**换手押格上发**一条**（默认 `span = thin`）：

```json
{"floor": 5, "eventType": "ColorTrack",
 "trackColorType": "Glow", "trackColor": "000000", "secondaryTrackColor": "ffffff",
 "trackColorAnimDuration": 2, "trackColorPulse": "None", "trackPulseLength": 10,
 "trackStyle": "Neon", "trackTexture": "", "trackTextureScale": 1,
 "trackGlowIntensity": 100, "justThisTile": true}
```

- `justThisTile: true` = **仅作用于当前方块** ⇒ 只改这一格，下一格自动恢复原色
  （**不需要**补一条恢复事件，也**不需要** `startTile/endTile/gapLength/duration/ease` ——
  那些是 `RecolorTrack` 的字段，**不要混进来**）
- **建关时逐格预演** ⇒ 那格**一出现就是霓虹**（「设置」语义）—— 没有「提前量」这种 hack
- ★ **一格一条、绝不堆叠**：用户拿编辑器截图指出过「几百条压在 floor 0 ⇒ 1/500」；
  现在每条事件就压在被染的那一格上（实测 `max_per_floor == 1`，单测 H 组守着）
- 另一档 `span = group`（整个双押组）⇒ 薄格 + 剩余格**各一条**，仍然一格一条
- 字段集**逐字对齐语料**：`core.colorize.EVENT_KEYS`（单测 F 组守着）

#### 2.2.1 被否掉的两种做法（留档，别再犯）
1. ✗ **`RecolorTrack` 压在被染那格** ⇒ 走过后才变色（用户第一次实测的原话）；
2. ✗ **`RecolorTrack` 提前到曲首发（`floor=0` + `startTile=[T,...]`）** ⇒
   几百个换手全堆在第 0 格，编辑器里「1/500」（用户第二次实测）。

## 3. 镜头调度规范（本轮只出设计）

### 3.1 不变量与会话模型

- **不变量**：屏幕上正在走的那条直线永远**水平**（与屏幕左右两条竖边垂直）⇒ 玩家**左右走**
- **拐角那一格全程不动**（含 90° / 三连音 / 预设图形内的所有小拐角）
- **出拐角后用短缓动回正**（实测允许短时斜）
- 实现方式：`relativeTo:"Player"` + `rotation:` 常量（0 或 ±90，**待真机标定**）+ `ease` 全部非瞬时

### 3.2 分派（用户选：元件 1+2+3 再加元件 4，按图形长短分派）

| 场合 | 动作 |
|---|---|
| 全程打底 | 元件 1（`rel=Player, pos=[0,0], rotation=CONST`） |
| 普通措辞处 | 元件 2 摆头 + 元件 3 缩放呼吸 |
| 90° 拐角 / 三连音 / 所有预设图形 | **镜头锁住不转**（只保留 1、3） |
| 短旋转图形 | 元件 4 短式：`rel=Player`，小角度转，`dur ≤ 2 拍` |
| 长旋转图形（雪花） | 元件 4 长式：`rel=LastPosition`，整圈数慢转，`dur = 段长`，`zoom` 同时拉满 |
| 段落边界 | `relativeTo` 按需切 `Player / Tile / LastPosition`，**切换点与图形边界对齐**（这是本设计相对 MM 的唯一自由化处：MM 里两者不同步） |

### 3.3 待标定量（实现前必须先测出来）

1. `rotation` 常量到底填几，才能让 `rel=Player` 下行星**朝屏幕右侧**走
   ⇒ 做一张 3 段测试谱（`rotation = 0 / +90 / −90`）进游戏看一眼即可
2. 「长图形」的阈值（建议候选：总转角 ≥ 360° 或 格数 ≥ 12），用你 MM1/MM2 的图形长度分布定
3. 缓动默认值：摆头 `±14° / 12 拍 / InBack→OutBack`；缩放 `250 ↔ 140`（重音砸 `1~25`）
