# 43 · 友项目时间戳：能不能用我们的逻辑拟合

> 用户 2026-10 给了一份外部时间戳（`Flower_Dance-DJ_OKAWARI-1974307.txt`，
> 1358 行纯整数毫秒），问「它能不能使用我们的逻辑进行拟合」。
>
> 复现脚本：`tools/_ext_ts_probe.py`（它是什么）、`_ext_ts_seg.py`（抖动还是分段）、
> `_ext_ts_cost.py`（拟合代价）、`_ext_ts_go.py`（真跑 `solve()`）。

***

## 0. 结论

| 问题 | 答案 |
|---|---|
| 这份数据是什么？ | **稳定的 151 ms 砖格 + ±6 ms 抖动**（不是分段变速） |
| 我们的模型**能不能**拟合？ | **能，而且能做到逐点精确** —— 因为 `travel` 是连续的，时间全靠它吸收 |
| 现在的 `solve()` 能不能直接吃？ | **不能**。它是**生成器**不是**拟合器**：实测 261 s 内累计漂移 **~155 ms** |
| 缺什么？ | 一个「**一砖一个音、travel 吸收 Δt**」的直拟合模式（`docs/25` 阶梯的落地） |

## 1. 它是什么（`_ext_ts_probe.py` / `_ext_ts_seg.py`）

```
1358 个时间戳 · 全整数 · 严格递增 · 无重复 · 691 → 262339 ms（跨度 261.6 s）
间隔：最小 47 · 中位 151 · 最大 790 · 104 种不同值
公共量子：1ms 当然都落，5ms 就 30% 不落，10ms 54% 不落 ⇒ **没有粗网格**
最常见间隔：151(38.8%) · 145(16.9%) · 157(8.1%) · 302(4.4%) · 150 · 146 · 296 · 156
```

**145/151/157 是抖动还是分段变速？**（这个判据很关键）

```
滑动窗口（24 个）中位间隔：从 ~51 s 起**一路 151.0**，窗口内 145~157
125/151/157 三者相邻切换率 57.8%
不同 100 条一段里三种都按相近比例混着出现（不存在「某段一种」）
★ 独立抖动时的「相邻相同」期望 = Σp² = 0.456；实测 = 0.422
```

⇒ **统计上与「独立抖动」无法区分**。三种值就是**同一个格子的 ±6 ms 噪声**，
不是三种 BPM。砖长稳定在 **151.0 ms** ⇒ `base_bpm = 60000/151 = 397.35`。

> ⚠️ 我第一版的结论判据是拿「57.8% 是否 > 60%」这种**瞎拍阈值**判的，得出了相反结论。
> 换成「实测 vs Σp²」才站得住 —— 记在这里，免得下次又拍脑袋。

## 2. 拟合代价（`_ext_ts_cost.py`，纯数据侧，可靠）

基准：一砖 = 151 ms（= 直线）。`travel = 180° × (Δt / C) / k`。

**A. 量化成整砖**（我们 default 的 `quantize_rhythm=True`）⇒ 换成**时间误差**：

```
中位 5.00 ms · 75分位 6.00 · 90分位 24.00 · 最大 75.00
>1ms 56.1% · >3ms 52.1% · >5ms 45.5% · >8ms 15.9%
```

**B. 保真**（`travel` 连续吸收）⇒ 换成**偏离直线的度数**：

```
|travel-180| 中位 5.96° · 90分位 28.61° · 最大 89.40°
>3° 52.1% · >7.5° 15.9% · >15° 12.3% · >30° 9.9%
```

**C. 抖动的小数部分**（43.6% 精确落格，还有一批落在**半砖**上）：

```
+0.00 砖 ×591 (43.6%)          ← 精确
+0.96 砖 ×272 (20.1%)  −6ms    ← 「差一点点到整砖」
+0.04 砖 ×129 ( 9.5%)  +6ms
+0.99 ×58 · +0.03 ×47 · +0.97 ×43
+0.54 ×17 · +0.58 ×13 · +0.46 ×10   ← ★ 落在**半砖**附近 ⇒ 需要 32 分音级细分
```

⇒ **两种拟合方向的代价是同一个旋钮的两端**：要它落在整拍上（好写谱）就得吃
中位 5 ms 的误差；要它时间精确就得接受中位 6° 的弯。**这份数据的抖动就是 6 ms 量级，
绕不过去。**

## 3. 真跑 `solve()`（`_ext_ts_go.py`）：它是生成器，不是拟合器

```
输入 1358 个音 · 跨度 261648 ms
自动（默认量化）           bpm 360.00  层 1359  直线  0.2%  换档 21   就近匹配中位 63.95 ms
自动 + 关量化             bpm 160.00  层 1359  直线  0.1%  换档  4   就近匹配中位 18.00 ms
手动 397.35 + 关量化       bpm 397.33  层 1359  直线 39.0%  换档 96   就近匹配中位 36.76 ms
手动 397.35 + 关模板/三连   bpm 397.33  层 1359  直线 42.1%  换档 78   就近匹配中位 61.82 ms
```

**为什么对不上**（看头尾就明白）：

```
输入 ts[:8] : 691 882 1091 1248 1399 1503 1678 1788
谱面 tm[:8] :   0 151  342  551  708  859  963 1138      ← 谱面轴从 0 起（少了 691 的 lead）
差值[:8]    : -691 -731 -749 -697 -691 -644 -715 -650
差值[-8:]   : -536 -536 -536 -536 -536 -536 -536 -536     ← ★ 尾部是**严格常量**
层数 1359 = 音数 1358 + 1                                  ← **没有乱插层**
```

尾部**严格常量**说明它在跟随；但早段 −691、尾部 −536 ⇒ **累计漂移约 155 ms**
（261 s 内 ≈ 0.06% 的相对速率差，但**绝对 155 ms 早就听得出来**）。

原因不是 bug，是**定位不同**：`solve()` 的活儿是「按几何把音铺成一条能走的路」——
它会为了 `travel ∈ [travel_min, 358]` 插层、为长休止用 `Pause`、为抑制极端档做
速度平滑。这些都会重新分配时间。**它不是「照抄时间戳」的工具。**

**顺带两条有用的**：
* 自动那套把 BPM 定在 360 / 160：它优化的是「一条直线 = 几拍」这种**音乐性目标**，
  不是「让众数间隔变成直线」。**手动 397.35 才有 39~42% 直线率**。
  ⇒ 需要一个「**按众数间隔定 BPM**」的入口（`docs/25` 对阶阶梯的落地）。
* 长空档只有 **1 个**（5.23 砖 = 790 ms）⇒ 这份数据基本没有休止，`Pause` 不是重点。

## 4. 所以「能不能用我们的逻辑拟合」

**能，但要用对的那一半。**

我们模型的自由度恰好是这件事的三件套：

```
base_bpm  → 决定「典型间隔 = 直线」（这份数据 ⇒ 397.35）
k（速度档）→ 离散倍率，处理大比例间隔
travel    → 连续，吸收每个间隔的**剩余部分**   ← ★ 时间精确全靠它
```

⇒ **一砖一个音、不插层、`travel = 180 × Δt / C / k`**，就能**逐点精确**复现这 1358 个
时间戳；代价是 §2-B 那张表（中位弯 6°、16% 弯超 7.5°）。

这就是一个**直拟合模式**，比 `solve()` 的 DP 简单得多。要实现的话：

1. **入口**：`base_bpm = 60000 / 众数间隔`（或让用户填「一砖 = 几 ms」）；
2. **模式**：`fit_direct`（一音一层，`travel` 由 Δt 反解，`k` 只在 travel 越界时才动）；
3. **报告**：把 §2 那两张代价表**直接上屏**（量化误差 / 偏离直线），让用户选要哪一端；
4. **细分**：那批落在半砖上的（3%）要么量化掉，要么允许 travel 更弯 —— 就是你说的
   「换算成 32 分音这种细分」那个方向。

**而 `solve()` 保持不动** —— 它的定位是「生成一份好谱」，不是「复刻别人的时间戳」。
两者输入相同、目标不同，不该混在一起。
