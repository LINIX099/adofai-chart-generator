# 44 · 去噪评估：先 BDG 吸附、再回我们这边拟合（开工前评估）

> 用户 2026-10：「我怀疑原始时间戳有随机抖动（**强化学习模型生成的，理论上绝对有抖动**），
> 那么可不可以先用 BDG 进行**吸附、去噪**，然后回到我们的工具去**拟合 & 生成**？」
> 参考插件：<https://github.com/BUGJI/bdg_plugin_import>

***

## 0. 结论

**方向对，但不必真的走 BDG。**

「BDG 里的吸附」在数学上就是 `snap_beat(beat, div)`，而 **`core/bdg/snap.py` 已经逐字
复刻了宿主的算法**（`js_round` / `round_prec` / `snap_beat` / `snapped`）。所以在我们这边
一次算完，结果与宿主内吸附**逐点一致**；BDG 那一趟的价值是**看得见、可复核**，
应当作为**可选的验证步骤**，而不是数据通路。

**关键实测**（拿那份 1358 个时间戳算的）：

| 事实 | 数值 | 为什么重要 |
|---|---|---|
| 砖长（众数间隔） | **151.0 ms** ⇒ `base_bpm = 397.35` | 网格必须用这个，否则吸附到错的格 |
| 抖动 | **±6.0 ms** | |
| 宿主默认吸附分母 | **4**（`DEFAULT_DIV=4`；档位 `[1,2,4,8,16,32]`） | 格 = 151/4 = **37.75 ms** |
| 抖动 vs 半格 | 6.0 < 18.9 | ⇒ 抖动**必然被吸收** |
| 最小间隔 | **47 ms** > 37.75 | ⇒ 分母 4 **不会撞点丢音**（分母 2 会，格 75.5ms） |
| 落在半砖的 | 约 3%（0.5 砖 = 75.5 = **2×37.75**） | ⇒ 也正好落在 1/4 格上，**不丢** |

⇒ **分母 4 既安全（不丢音）又够用（吸收抖动）**。这是宿主自己的默认值，巧合但很合适。

去噪后所有点落在 37.75ms 格上 ⇒ 我们这边的「直拟合」**逐点精确**
（`travel = 180 × Δt/C = 45° × m`），而且 **`solve()` 那个 155ms 累计漂移的问题不再存在**
—— 因为不再需要它去重分配时间。

## 1. 走 BDG 路线的**手动依赖**与风险（要写进流程里）

| 项 | 情况 |
|---|---|
| **吸附开关** | ★ 插件 API **没有**吸附/分母的接口（`api.ui` 只有 panel/action/shortcut）⇒ 只能**用户手动**开吸附、设分母 |
| **BPM/offset** | 我们能设（`setBaseBpm`/`setOffset`）⇒ 这半边是自动的 |
| **吸附没有半径** | 宿主是**全部吸附**（`store.snapped`），不是「就近去噪」⇒ 会挪动**每一个**点。格够细（37.75ms）时中位挪 ~5ms、最大 18.9ms，可接受；**但若分母设成 1，最大挪 75ms ⇒ 会毁掉那 3% 半砖的音** |
| **撞点丢音** | `addMarker` 撞到已有拍位会返回 null（`store.ts:669`）⇒ 分母≥4 时实测安全（最小间隔 47ms） |
| **多一步人工** | 推送 → 用户开吸附 → 收回；中间他还可能顺手改动别的东西 |

⇒ 所以我建议：**默认在我们这边一次算完**（同数学、零人工），
BDG 那趟留作**「我想亲眼看看吸附成什么样」**的复核路径。

## 2. 参考插件 `bdg_plugin_import` 告诉我们什么

（已拉取核对，5 个文件的小仓库）

```js
api.ui.registerImporter({ label, run })          // 菜单「文件 → 导入…」多一项
api.system.pickFile({ title, filters })          // ★ 插件**能开文件选择器**
api.system.readText(path)                        // ★ 插件**能读文件**
api.system.writeText(path, content)              // ★ 还能写（本地宿主 .d.ts 已确认）
api.project.edit.addTrack({ name })              // 建**内置轨**（和我们现在的做法一致）
api.project.beatOfTime(ms)                       // ms → 拍
api.project.edit.batch(fn)                       // 一次撤销
```

三条对我们有用的结论：

1. **插件能读文件**（`pickFile`/`readText`/`writeText` 都在当前宿主 API 里）——
   我们以前假设「只读 renderer 插件拿不到文件系统」，**那是错的**。
   ⇒ 以后「连接串要手贴」「要导入/导出一份编排」这类体验问题，可以在插件侧解决。
2. 它的做法（`addTrack` + `beatOfTime` + `batch`）与我们 **完全一致** ⇒ 我们在正道上。
3. ★ **它没有设 `baseBpm`/`offset`** —— README 原话是「落到**当前 BPM** 时间轴上」，
   也就是**用户得自己先把 BPM 弄对**。这正是你踩的坑 #2，说明**只有我们在填这个坑**
   （`setBaseBpm`/`setOffset` + 发毫秒让插件换算）。

> 顺带：它的 `plugin-api.d.ts` 是 6301 字节的旧快照，本地宿主那份是 6519 —— 差的不多，
> 但**以本地这份为准**（我们所有断言都对着它）。

## 3. 开工计划（压缩后按这个顺序）

**① `core/denoise.py`（新）—— 网格拟合 + 去噪**

```python
grid_fit(ts)                      # 估「周期 + 相位」：众数间隔 + 最小二乘相位
denoise(ts, div=4, radius=None)   # 吸附；radius=None = 全吸（与 BDG 一致）
                                  # radius=12 → 只吸「离格 <12ms」的，其余**保留并报出**
```

★ **`radius` 是我加的、BDG 没有的东西**：宿主是「全吸」，所以我们提供
「全吸（一致）」和「带半径（保真）」两种，并把**超过半径的**逐条报出来让你决定。
报告要有：每点挪了多少（中位/p90/max）、有多少撞点、有多少超出半径。

**② `fit_direct` 模式（新）—— 直拟合**

一砖一个音、不插层：`travel = 180 × Δt / C / k`，`k` 只在 travel 越界
（`[travel_min, 358]`）时才动。输出谱面 + **直线率** + **量化残差**。
（依据：`docs/43` §2 的代价表 —— 量化端中位 5ms，保真端中位弯 5.96°。）

**③ 报告上屏**（走现成的 `warning_list`）

把①②的两张代价表直接印出来，让你一眼看出「这次拟合是偏时间还是偏直线」。

**④ 可选：BDG 侧加一个 importer**（照参考插件）

让我们能「把时间戳丢进 BDG 看吸附结果」。成本低（我们已有 junction 安装 + 插件骨架
+ `bridge_plugin` 那套实现），但**建议放在①②之后** —— 先看①的报告，再决定要不要走这一趟。

**⑤ 顺序建议**：先做 ①②（我们这边闭环、零人工），拿这份 `Flower_Dance` 的真实数据
验收：去噪后应当**逐点落格、直拟合 0 残差**；再决定 ④。

## 4. 还没定/要盯的

- **`radius` 默认值**：全吸（与 BDG 一致）还是带半径（保真）？我倾向**默认全吸 + 报告**，
  因为你要的是「去噪」；半径那档留给你手动。
- **吸附分母**：默认 4（宿主默认、实测安全）。要不要按「最小间隔 / 2」自动推导一个安全下限，
  避免分母太粗撞点丢音？我倾向**自动推导 + 报出来**。
- **相位**：BDG 的格是 `beat` 的整数倍（相位锚在 `offsetMs`），所以相位由我们的 `offset`
  决定 —— 也就是「去噪的相位」和「我们交给宿主的锚」是同一个东西，不能分开调。

## 5. 定稿（用户 2026-10：「直接按照合适的来」）

三个待定项按本文的倾向定了，并且**已经落地**（实现与实测 = `docs/45-收回轨道项目.md`）：

| 待定项 | 定稿 | 备注 |
|---|---|---|
| `radius` | **默认全吸**（`radius=None`，与 BDG 一致）；给半径才是保真档 | 报告里会说几个点被原样保留 |
| 分母 | **自动**：最细但仍 `step ≤ 最小间隔` 那一档，上限 1/32 | 真数据上自动选中 **1/4**；到上限会明说 |
| 相位 | 拟合，给了 `offset` 就用 offset 并报「差几格」 | 桥接锚在直拟合+去噪时改用**格相位 φ**（3.5 节） |

★ 另外两个本文没预见、实现时才暴露的坑（值记在这里）：

1. **本文的「砖长 151.0ms / bpm 397.35 / 抖动 ±6ms」是**初测近似值**。精修之后真值是
   **150.000ms / 400.000bpm**（那份 RL 数据就是按 400 BPM 生成的），抖动实测
   **中位 2.3ms / p90 7.9ms / max 18.4ms**（不是 ±6ms 那么整齐）。
2. **用 `gridfit` 的拍级集中度 R 去精修周期会被抖动骗走**（实测落到 148.99 / 相位 92.3，
   于是每个点都吸到邻格）⇒ 判据改成「格内平方残差」，见 `docs/45` §1.3。
