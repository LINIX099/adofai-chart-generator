### 1.3 解析坑（三个，都踩过）

1. **BOM**：游戏写出的 `.adofai` 是 UTF-8 **with BOM** ⇒ 必须 `utf-8-sig`，否则 `json.load` 抛 `Unexpected UTF-8 BOM`。
2. **尾逗号**：手动删过事件的版本会留 `,}` / `,]`（`Hello2025_完全去特效`、`gamma/level_old`）。
3. **字符串里的裸控制字符**：`CFM1\main.adofai` 第 9137 行有一个裸控制字符 ⇒ 严格模式抛 `Invalid control character`。
   **修法**：`json.loads(txt, strict=False)` + 先去掉尾逗号。
   （我第一版用正则自己清 `[\x00-\x08\x0b-\x1f]`，**漏了 `\t\r\n`** —— 它们同样是严格模式拒绝的字符，于是 CFM1 整份被跳过，
   差点把一个用户点名的语料当成"没有数据"。现在两份报告都能读到 CFM1\main.adofai：8890 actions。）

★ 教训：**"语料里没有 X" 必须先排除"我的解析器读不进去"**。这和 `docs/59` 那次 `INTEREST` 白名单造成的观测盲区是同一类错误。

## 2. 事件全家谱：谁碰得到轨道

`‹游戏反编译源码目录›\ADOFAI\LevelEventType.cs` 里共 **71 个事件**。筛完之后分 5 组：

### L1 轨道本体外观（改"这块砖长什么样"）
| 事件 | 面板名 | 关键字段 | 语义 |
|---|---|---|---|
| `ColorTrack` | **设置**轨道颜色 | `trackColorType/trackColor/secondaryTrackColor/trackStyle/trackTexture/trackGlowIntensity/floorIconOutlines/justThisTile` | Build 期按 floor 预计算 ⇒ 砖块**出生就是这个颜色**；`justThisTile=true` ⇒ **只这一格**，下一格自动恢复（`docs/59` 用的就是它） |
| `RecolorTrack` | **重新设置**轨道颜色 | 上面 + `startTile/endTile/gapLength/duration/ease/angleOffset/eventTag` | 运行时在**时间经过该 floor 之后**才把 `startTile..endTile` 刷成新颜色；**是持续状态**，要恢复得再写一条 |
| `TrackSettings` | 轨道设置（**settings 字段，不是 action**） | `trackAnimation / beatsAhead / beatsBehind / trackDisappearAnimation` | 全局出场/消失动画，我们 `writer.build_json` 已经在写 |
| `TileDimensions` | 格子尺寸 | — | **8 份语料 0 次**，字段未验证 ⚠ |
| `SetFloorIcon` | 格图标 | — | 8 份语料 0 次 ⚠（`ColorTrack` 里倒是有 `floorIconOutlines`） |

### L2 轨道运动（砖块的位置/旋转/透明度/缩放）
| 事件 | 关键字段 | 语义 |
|---|---|---|
| `MoveTrack` | `startTile/endTile/gapLength/duration/ease/positionOffset/rotationOffset/scale/opacity/angleOffset` | 给**一串格子**做位移/旋转/缩放/透明动画。`positionOffset` 单位=格，`[null,x]` 表示"只动这个轴"；`duration` 单位=**拍** |
| `PositionTrack` | `positionOffset/rotation/scale/opacity/relativeTo/justThisTile/editorOnly/stickToFloors` | 改**单格**的静态位置（`docs/58` 已在用，给重叠图形标注"第几圈"） |

> ★ 关键陷阱：`core/writer.py` 里 `PositionTrack` 的字段是**逐字对齐**过的（`editorOnly` 是字符串枚举，多写 `relativeTo/justThisTile/ease/duration` 会 `NullReferenceException`）。语料里能用的 `relativeTo/justThisTile` 是**v19** 的写法。
> 详见 `writer.build_actions` 里的注释。

### L3 显隐 / 出入场
| 事件 | 关键字段 | 语义 |
|---|---|---|
| `MoveTrack`(opacity) | `opacity: 0` | **真正"让砖块消失"的手段**（没有独立的 hide 事件） |
| `AnimateTrack` | `trackAnimation / trackDisappearAnimation / beatsAhead / beatsBehind` | 从这一格起改变**出场/消失动画**；两种枚举见 §3.3 |
| `Hide` | `hideJudgment / hideTileIcon` | ⚠ **不隐藏砖块**，只藏**判定文字**和**格图标**（`hideJudgment=True` = 关掉判定显示的密集段读谱辅助） |
| `ChangeTrack` | — | 8 份语料 **0 次**，未验证 ⚠（Taro DLC 相关） |

### L4 全局后期 / 屏幕（影响"轨道看起来怎样"，但不属于轨道本身）
`SetFilter`(35 种滤镜) · `SetFilterAdvanced`(CameraFilterPack 60+) · `Bloom` · `Flash` · `ShakeScreen` · `HallOfMirrors` · `ScreenTile` · `ScreenScroll` · `SetFrameRate` · `ScaleRadius` · `ScaleMargin` · `ScalePlanets` · `SetPlanetRotation` · `MoveCamera`

> 其中 `ScaleRadius/ScaleMargin/ScalePlanets` 改的是**星球环/星球大小**，会直接改变"轨道在屏幕上的观感密度"，算半个轨道事件。

### 与轨道无关（48 个，本轮不用）
- **时序类**：`Twirl`(22098) · `SetSpeed`(7775) · `Pause` · `Checkpoint` · `Multitap` · `FreeRoam*` · `AutoPlayTiles` · `SetInputEvent` · `KillPlayer` · `ScaleMargin`…（这些动的是**怎么走**，不是**长什么样**）
- **装饰/文字/物件/粒子**：`AddDecoration` · `MoveDecorations`(48940!) · `AddText` · `SetText`(3724) · `AddObject` · `SetObject` · `AddParticle` · `SetParticle` · `EmitParticle`
- **音频/元数据**：`SetHitsound` · `PlaySound` · `EditorComment` · `Bookmark`

## 4. 真实套路库（★ 这一节才是有用的东西）

每个套路给「**配方 + 出处 + 原文**」。三条都是从语料原文里逐字抄的。

### 4.1 P1 · 砖块消散（`MoveTrack` on 上一格）— 出现频率第一

**配方**
```
floor            = 当前格
startTile/endTile= [-1, "ThisTile"]        ← 只作用于"刚走过的那一格"
gapLength        = 0
opacity          = 0
positionOffset   = [dx, dy]                ← 往哪飞
scale            = [sx, sy]                ← 压扁/拉长/缩到 0
duration         = 4~32                    ← 单位=拍
ease             = InCubic / InCirc / InElastic / InExpo
```

**出处（真心话：这是重型谱的通用语法，8 份里 6 份都在用）**

CFM1 的三种变体（`main.adofai`，160bpm）：
```json
{"floor":N,"eventType":"MoveTrack","startTile":[0,"ThisTile"],"endTile":[0,"ThisTile"],"gapLength":0,"duration":128,"positionOffset":[-12,-12],"opacity":0,"ease":"InExpo"}   ← 411 条：慢慢飞走
{"floor":N,"eventType":"MoveTrack","startTile":[-1,"ThisTile"],"endTile":[-1,"ThisTile"],"gapLength":0,"duration":7,"positionOffset":[null,-5],"opacity":0,"ease":"InCubic"}  ← 299 条：往下掉
{"floor":N,"eventType":"MoveTrack","startTile":[0,"ThisTile"],"endTile":[0,"ThisTile"],"gapLength":0,"duration":7,"positionOffset":[0,0],"rotationOffset":0,"opacity":100,"ease":"OutBack"} ← 299 条：弹回来
```

MM1 vvfx（`level_vvfx.adofai`）：
```json
{"floor":N,"eventType":"MoveTrack","startTile":[-1,"ThisTile"],"endTile":[-1,"ThisTile"],"gapLength":0,"duration":4,"scale":[0,0],"ease":"InBack"}      ← 237 条：塌缩
{"floor":N,"eventType":"MoveTrack","...","scale":[200,200],"opacity":5,"duration":0,"ease":"Linear"}                                                     ← 233 条：瞬间压成亮片
```

**为什么"挂上一格"就不用回收**：玩家已经走过去了，那格在 `beatsBehind` 之后本来也会消失。
⇒ 和 `docs/59` 里 `ColorTrack + justThisTile` 是**同一个"避免状态污染"的思想**，只是搬到了 `MoveTrack`。

### 4.2 P2 · 抹掉历史（瞬间清空）— 换段/卡点的"清场"

```json
{"floor":N,"eventType":"MoveTrack","startTile":[-1,"ThisTile"],"endTile":[-200,"ThisTile"],"gapLength":0,"duration":0,"positionOffset":[null,null],"opacity":0,"ease":"Linear"}
```
- `endTile` 给一个**绝对值很大的负数**（`-100 / -200 / -500`），`gapLength=0` ⇒ 把"前方 100~500 格"一次刷成 opacity 0。
- `duration=0` + `Linear` ⇒ **瞬发**。语料里 `-200`(13 条) / `-500`(6 条) / `-100`(4 条)。
- 也有用「绝对下标」写整段区间的：`startTile:[121,"Start"], endTile:[0,"End"]`。

★ 这条**只在 `beatsBehind>0` 之外的场景才有意义**（否则格子本来就会消失）；它是"提前让前方空地"。

### 4.3 P3 · 涟漪环（`RecolorTrack` 同心圆）— Hello2025 的招牌

**配方**（对 n = 0..N）
```
floor       = 同一个 floor
startTile   = [-n, "ThisTile"]
endTile     = [+n, "ThisTile"]
gapLength   = 2n - 1          ← ★ 步长 = 2n ⇒ 只刷到 ±n 两侧各一格
angleOffset = 30 * n          ← ★ 每环晚 30° = 1/6 拍
duration    = 0  → 再补一条 duration=2、颜色回落的
```

**原文**（`Hello (BPM) 2025.adofai` floor 6811，**一格 171 条 RecolorTrack**，成对出现）：

## 5. 时间轴对齐（★ 我们真正要用的钩子）

### 5.1 `angleOffset` 的单位 = 「180 = 1 拍」

源码实证（`vendor\Re_ADOJAS\src\lib\Player\TimelineManager.ts:156-166`）：
```ts
const angleOffset = ep.angleOffset;
let timeOffset = (angleOffset / 180) * secPerBeat;
const eventTime = startTime + timeOffset;
```
⇒ **`angleOffset = 180` 就是「延后整整一拍」**，`30` = 1/6 拍，`-90` = 提前半拍。

这和我们已有的时间模型**天然同构**（`core\path.py`：`travel = 180 − |ΔangleData|`，`180` = 直线 = 1 拍）。
所以：
```python
# 想把事件放在「第 i 格内、走过 travel_frac 比例」的位置：
angleOffset = travel_i * frac          # frac=0 → 格首, 0.5 → 格中, 1.0 → 下一格首
# 想放到「第 i 格之后 dt 拍」：
angleOffset = 180 * dt / speed_k_i     # speed_k = 该格 BPM 倍率的倒数（见 track_fx.beat_positions）
```
并且 `angleOffset` **可以超过单格 travel**（语料里 `-2880 / -5760 / 1440 / 11520` 满地都是）
⇒ 它会自然落到后面的格子里 —— 这正好是 `RepeatEvents` Beat 模式能工作的原因（§5.4）。

### 5.2 `MoveTrack` 的 `duration` 单位 = 拍（源码实证）

```ts
const rawDuration = (action.duration ?? 1) * secPerBeat;   // TimelineManager.ts:174
```
⇒ `duration: 8` = 8 拍（按**该格的BPM**换算）。`duration=0` 会被兜底成 1 帧级（源码 `|| 1`）。

### 5.3 `gapLength` = **步长**（不是"间隔多少格"）

```ts
for (let i = start; i <= end; i += 1 + gapLength) { ... }   // TimelineManager.ts:177
```
⇒ `gapLength=0` → 逐格全刷；`gapLength=1` → 刷 1,3,5…；`gapLength=7` → 刷 1,9,17…
⇒ **P3 涟漪环就是靠这个**：`startTile=-n, endTile=+n, gapLength=2n-1` ⇒ 步长 2n ⇒ 恰好刷 ±n 两点。

⚠ 该循环里 `if (i < 0) continue;` ⇒ **负下标（格 0 之前）被忽略**，所以 `startTile=[-200]` 在开头几格上只是"能刷多少刷多少"。

### 5.4 `RepeatEvents` = 官方自带的"算法调度器"（能省掉 N 条 actions）

```json
{"floor":253,"eventType":"RepeatEvents","repeatType":"Beat","repetitions":15,"floorCount":1,"interval":16,"executeOnCurrentFloor":false,"tag":"42"}
```
- 它**只认 `tag`**：被重复的是"**同一 floor 上、`eventTag`（或 `tag`）等于它的那些事件**"。
- Beat 模式（源码实证 `TimelineManager.ts:120-123`）：
  ```ts
  repAngleOffset = info.interval * rep * 180;   // ⇒ interval 单位就是"拍"
  ```
  ⇒ 事件**留在原 floor**，靠 `angleOffset += 180·interval·rep` 把时间铺开。`repetitions=15, interval=16` ⇒ 铺 16 拍 × 16 次。
- Floor 模式：事件搬到 `baseFloor + rep*gapLength`，或把位移换算成 `angleOffset`。
- 语料用法：`Interval` 众数是 `8/4/1/32/2/16`（**2 的幂**），`repetitions` 众数 `15/7/3/8/31`（**2^n − 1**）⇒ 作者是拿它当"每 4 拍来一次，来 16 次"的循环器。

★ **这是"算法轨道调度"的现成压缩器**：我们若做周期性变化，应该优先用 `RepeatEvents` + 一个 `eventTag`，
而不是写 64 条事件（语料里 `CFM1` 用 68 次重复的 `fufu1`，`2024_vvfx` 用 100 次重复的 `a`）。

### 5.5 状态模型（**设计时必须先定**）

| 方式 | 代表事件 | 优点 | 代价 |
|---|---|---|---|
| **A 出生即定** | `ColorTrack + justThisTile:true` | 零回收、绝无"污染后一格" | 每格一条（171 条/格那种就别想了） |
| **B 设状态 + 靠持久** | `RecolorTrack`（不带 `justThisTile`） | 一条管到下一次设置，**极省** | 必须自己记账"什么时候恢复" |
| **C 只碰走过的格** | `MoveTrack` on `[-1,"ThisTile"]` / `ColorTrack justThisTile` | **不需要回收**（玩家已走过） | 只能做"落幕"，不能做"预告" |
| **D 压缩重复** | `RepeatEvents` + `eventTag` | actions 数量级下降 | 只能周期性、且 Tag 是全谱命名空间（会撞名） |

## 6. 对我们的可行性分档

判定标准：**(1) 只写 `actions`、不碰 `angleData`/`bpm`/`travel`（时序零影响）；(2) 我们自己的 beat 网格能算出它；(3) 不引入"需要回收的状态"。**

### A 档 · 低风险，可以直接进功能
| 算法 | 用的事件 | 我们的驱动信号 | 量级估计 |
|---|---|---|---|
| **涟漪环** P3 | `RecolorTrack`（±n 环） | 段落起点 / 强 onset | 一个环 ~2N 条（N=环数），**建议 N≤24** |
| **每格自色/脉冲** P5 | `ColorTrack justThisTile` + `trackColorPulse` | 换手押（已有）/ 图形起点 | 与 `docs/59` 完全同构，只是换配色 |
| **出场动画** P6 | `AnimateTrack` / `settings` | 段落密度（密段 `beatsAhead` 短） | 常数条 |
| **读谱辅助** P11 | `Hide` | 高密度段（音符/秒 超阈值） | 常数条 |
| **星球环脉冲** P9 | `ScaleRadius` | 拍点 | 1 条/拍 ⇒ 用 `RepeatEvents` 压 |
| **砖块消散（走过的格）** P1 | `MoveTrack` on `[-1]` | 强 onset（"这一下打得重"） | 1 条/触发点 |

### B 档 · 需要先设计状态机 / 需要真机标定
| 算法 | 问题 |
|---|---|
| **逐格多米诺** P4 | 同格 53~133 条 `MoveTrack`（MM1/gamma 的体量）；我们必须有"上限 + 采样"策略，否则 actions 爆炸 |
| **抹掉历史** P2 | 只在 `beatsBehind>0` 的场景有意义；现在的观感依赖默认 4 拍，改成"永留"还是"擦除"要先定 |
| **滤镜包络** P7 / **闪光抖屏** P8 | 改的是**整个画面**（含背景），不属于"轨道"，而且会显著影响读谱 —— 要做需要你点头 |
| **`RepeatEvents` 压缩** | 要先有"全谱 tag 唯一性"的分配器（现在没有任何 tag 管理） |

### C 档 · 建议不做
- **装饰/文字/物件/粒子**（`MoveDecorations`/`SetText`/`AddObject`/`AddParticle`…）：这是**另一套系统**（有自己的坐标/视差/遮罩），且语料里它们是**手工美术件**，没有可算法化的公式。
- **`ChangeTrack`/`TileDimensions`/`SetFloorIcon`/`SetDefaultText`**：**社区语料 530 份里 `ChangeTrack` 0 次、`TileDimensions` 0 次、`SetFloorIcon` 0 次**（§10.3）⇒ 没有可抄的真值，盲写有 `NullReferenceException` 风险。
- **`HallOfMirrors`/`ScreenTile`/`ScreenScroll`/`SetFrameRate`**：整屏几何变换，和"轨道调度"关系不大，且极端影响可读性。

### 10.1 四条路 + 语料实测占比

### 10.2 `trackTexture` 的真相（★ 重要）

- 社区语料 530 份里，`settings.trackTexture` **非空 0 份**；事件侧非空 **只有 4 处**。
- 为什么没人用：① 只有 `ColorTrack` 带 `trackTexture`（`RecolorTrack` 的 18 个字段里**没有**它）；
  ② 贴图只换"砖块表面纹理"，不换形状，但**要求贴图文件跟谱面一起分发**（工坊/Worlds 目录里必须有）；
  ③ 官方 `trackStyle` 的 6 种皮肤已经覆盖大部分审美。
- `trackTextureScale` 出现过 `25`/`30` 这种值（配空贴图），说明它有"缩放平铺"的语义，但**社区语料不足以验证** ⚠。

### 10.3 「改方块形状」的官方事件 = `TileDimensions`，但**社区语料里 0 次**

反编译实证（`scnGame.cs:481-484`，注意 `scnGame.cs:1174-1175` 是同一件事的另一处）：
```csharp
case LevelEventType.TileDimensions:
    lengthMult = item5.GetFloat("length") / 100f;   // 字段名就是 length / width（百分比）
    widthMult  = item5.GetFloat("width")  / 100f;
```
⇒ 它能把砖块**拉长/拉宽**（`floor.lengthMult / widthMult`）。但 **530 份语料里 0 次使用**，也没有任何字段真值可抄 ⇒ **不建议碰**（未验证字段 + 可能 `NullReferenceException`）。

### 10.4 一条必须记住的字段语义（来自 `AnimateTrack` 的实现）

`scnGame.cs:468-479`：
```csharp
case LevelEventType.AnimateTrack:
    flag2 = !item5.disabled["trackAnimation"];
    if (flag2) { animationType = (TrackAnimationType)item5["trackAnimation"]; num3 = item5.GetFloat("beatsAhead"); }
    if (!item5.disabled["trackDisappearAnimation"]) { ... }
```
⇒ `LevelEvent` 有一个 **`disabled` 字典 = "这个字段这次要不要覆盖"**。
所以 `AnimateTrack` 可以**只写要改的字段**（语料里确实存在只有 `floor/eventType/beatsAhead/beatsBehind` 的 `keys(4)` 写法，且能正常工作）。
**规则**：`AnimateTrack` 只写要改的字段；而 `ColorTrack/RecolorTrack` 是"整状态"事件（`docs/59` 的写法 = 全字段），两者不要混。

### 10.5 对"非常优秀的水准 + 不用默认方块"的可执行结论

1. **R1 是主力**：`trackStyle` 从 `Standard` 换到 `Neon / Gems / NeonLight` + `trackColorType: Glow` + `trackColorPulse: Forward`，
   这一步就能让画面完全脱离默认方块，**且是零风险的纯 `actions`/`settings` 改动**。
2. **R3 做"疏密节奏"**：`ScaleRadius` 150/180/250 在段落间切换（1517 条的社区用法），做出"轨道呼吸"。
3. **R4 做"读谱"**：密集段 `Hide(hideJudgment=true)`。
4. **R2 基本可以放弃**（除非你愿意为每一格准备贴图，且接受"贴图要跟谱面一起分发"）。
5. **R5（装饰序列帧）才是"重型特效"的真相，但它不是"轨道调度"** —— 要做请单独立项，不要塞进这一轮。

### 12.1 分层与优先级

|---|---|---|

| L2 | **算法层**（本轮新增）：涟漪环（`RecolorTrack`）+ 半径调度（`ScaleRadius`） | 中，**必须避让 L1 已占用的 floor** |

### 12.2 涟漪环（结构驱动，§4.3 的配方）

- **触发点**（待定，多选）：① 段落起点（`core/segments.py` 的边界）② 预设图形起点（`core/figures.py`）③ 换手押链的**链头**双押
- **环数**：`N = min(appearance_ripple_rings, 到下一个触发点的格数 // 2)`
- **每环**（n = 0..N）：
  ```
  floor        = 触发格
  startTile    = [-n, "ThisTile"]
  endTile      = [+n, "ThisTile"]
  gapLength    = 2n - 1
  angleOffset  = step * n          （step 默认 30° = 1/6 拍）
  trackColorType/Style/Glow     = L0 皮肤
  trackColor   = 主色（默认 ffffff）
  duration     = 0（瞬发）；n 环结束由"回色事件"收
  ```
- **预算**：约 `2N + 1` 条/触发点。不设总量上限，但**同格并行度上限 128**（Hello2025 实测 171 是全场最高）

### 12.3 半径调度（结构驱动：密度）

- **密度度量**：滑动窗口 `W`（默认 8 拍）内的**音符数 / 秒**（用 `core/track_fx.beat_positions` 的拍轴算）
- **映射**（方向待定）：档位 → `ScaleRadius.scale`；建议数值直接抄语料主流 **100 / 150 / 250**
- **写法**：只在**档位变化**时写一条（`ScaleRadius` 是持续状态 ⇒ 天然无需回收）
- **量级**：约"档位切换次数"条，通常 < 50

### 13.2 只有两条硬防护（用户口径「不设上限」）

1. **同格并行度上限 128**（`MAX_PER_FLOOR`）：涟漪环是唯一会同格多条的，超了截断并报数。
2. **环数不越过谱首/谱尾**：`cap = min(rings, 触发格, 层数−1−触发格)`
   （负下标会被游戏忽略，`TimelineManager.ts:178` `if (i < 0) continue`）。
   ★ 另外 `gapLength` 取 `max(0, 2n−1)` —— **n=0 时必须是 0**，
   写 −1 会让游戏的 `i += 1 + gapLength` 步长变 0 ⇒ **死循环**（单测 C 组守着这条）。

### 13.3 密度口径（为什么阈值能写死）

`density_tpb = (窗口内格数 − 1) / 拍跨`（**边到边**）：

| 演奏形态 | 格/拍 |
|---|---|
| 全 180° 直格（1 拍 1 格） | 1.0 |
| 全 90° 格（1 拍 2 格） | 2.0 |
| 全 45° 格（1 拍 4 格） | 4.0 ← 密集阈值 |
| 全 30° 格（1 拍 6 格） | 6.0 |

`beat_positions` 用的是**基准 BPM 的拍轴**（不含 `base_bpm`）⇒ 与曲子 BPM 无关；
而 `speed_k` / `pause_beats` **会**影响它（它们真的改变了"每秒几个音"），这是有意的。

### 13.5 已知取舍（**不许静默**）

1. **涟漪环在同格堆多条是设计**：一格 34 条（17 环 × 闪+回色）。语料 `Hello2025` 实测**一格 171 条**。
   ⑤b 那次的教训是「**语义**要一出现就可见」，**不是**"同格多条一定错"——这里每环的
   `startTile/endTile/gapLength/angleOffset` 都不同，是波前的每一环。
   （若你在编辑器里看到「1/34」觉得碍眼，可以把「最多几环」调小。）
2. **半径切换点被密度窗口提前/滞后约半个窗口**（±4 拍）：平滑换来的。实测 段3 起点 33 → 切换 36；

3. **皮肤是全局兜底**：`settings` 一旦改成 Neon，**整谱**都变（包括换手押段）。
   ⑤b 的 `ColorTrack` 是逐格覆盖 ⇒ 两者不打架（⑤b 那一格仍是黑底白边）。
4. **`ScaleRadius` 的另一半（星球是否跟着走）** 反编译只能证据到"初始位置取自
   `floors[i].transform.position`"，运行中的 `scrPlanet.cs` 不在反编译里 **⚠ 未 100% 实证** ——

### 14.4 ★★ 抓到的真错误：密度的单位不能用「格/拍」

第一次生成（`docs/60` §12 那一版）报出：

```
半径切换 2 处: [(294, 250), (298, 100)]      ← 4 格内 250→100，闪了一下
```

**根因**：`density_tpb` 的「拍轴」只吃 `travel/speed_k`、**不吃 `base_bpm`**，
而这条流水线的 auto-BPM 会把同一首音乐标成 **122.5** 或 **980**（差 8 倍）⇒
同一个阈值「4 格/拍」在两种标法下对应的真实密度是 **8 音/秒 vs 65 音/秒**，
阈值在音乐上根本没有意义。

**修法**：密度改成 **音/秒**（`density_fps`，纯实时量：
`格/拍 × base_bpm/60`），阈值默认 **密 ≥8 / 疏 ≤5**，并且防抖从"只按拍数"
升级成 **「≥1 秒 且 ≥8 格」双条件**（980 BPM 下 4 拍只有 4 格，只按拍数挡不住）。

修完后同一个谱：**半径切换 1 处 `(78, 250)`** —— 从轮指段开始摊开，不再闪。
新参数：`appearance_dense_fps` / `appearance_quiet_fps` / `appearance_radius_min_sec`
/ `appearance_density_window`（秒）。单测 F/G 组已按新口径重写并加了"3 格尖峰不许闪"这一条。

### 14.5 顺带发现（**未改，只记录**）

1. **直拟合那条路不认 `auto_bpm`/`base_bpm`**：`session` 的 `FIT_DIRECT` 分支用
   `fitdirect.build(base_bpm=(xk_cbpm or 去噪网格的 bpm))`，所以传进去的
   `auto_bpm=false, base_bpm=122.5` **被忽略**（实测仍是 979.912）。
   `base_bpm` 框在 schema 里本来就被标成"只回填显示"，最优化路径也吃它；
   唯独直拟合路径吃的是去噪网格 —— **这是既有行为，不属于本轮**，要改得先问用户。
2. **`adofai_to_ts.py` 的简化时间模型在 `Pause` 多的谱上会偏**：
   实测对 ASGORE 整谱偏 +8230ms、对我们导出的谱偏 −3796ms（第三方 parser 为准）。
   已在工具里加**主动自检**（差 >20ms 就明说"抽出来的不可信"），不再静默出错。
   ⚠ 我们这次用的**前 62 秒**窗口实测只偏 ≤61ms（第三方 parser 交叉验证过），所以结果有效。
3. **直拟合不产图形段** ⇒ 涟漪环 0 处。要在这类谱上看到涟漪，得让求解走最优化路径
   （会牺牲时序精度），或者以后给直拟合加"图形段标记"。

## 15. ★★ 那一版**是碎的** —— 我校验了时序，却从没校验几何（用户 2026-10 截图追问）

用户把 `out\ASGORE轮指60s` 放进游戏，截图回来：「**为什么碎成这样了 你觉得这对吗**」。
**不对。** 这是本轮的真正教训，比任何功能都值钱。

### 15.1 碎成什么样（量出来，不是感觉）

`tools/read_adofai.py` 现在带 **★ 几何体检**（`core/geomcheck.py`）：

| 配置 | 直线率 | 发卡弯 | 回折率(\|Δ角\|≥135°) | **重叠对** | **每格占地** | 结论 |
|---|---|---|---|---|---|---|
| 直拟合 · 860 音（**我当时交付的**） | 41.7% | 27.4% | 17.9% | **1192**（1.39/格） | **3.7 格²** | ✗ 碎 |
| 最优化 · 860 音 | 5.9% | 63.4% | 53.8% | **2572**（2.99/格） | **0.7 格²** | ✗ 更碎 |
| 最优化 + 激进采音阶梯 · 860 音 | 6% | — | — | — | — | ✗ 还是碎 |
| 直拟合 · **合并 60ms** · 545 音 | **96.9%** | 0.2% | 0.2% | **17**（0.03/格） | **198 格²** | ✅ 一条路 |
| 源谱 ASGORE（人写的，5268 格） | 31.2% | 24.8% | 24.6% | 537（0.10/格） | 97 格² | 有结构的折返 |
| 我们的常规导出 MemoryLocked | 66.2% | **0%** | **0%** | 25（0.02/格） | 59 格² | ✅ |

**碎渣的签名 = "高重叠 + 每格地皮极小"**，不是"折返多"（源谱折返 24.6%，但每格占地 97 格²）。

### 15.2 根因（两层）

1. **输入层**：借用别人的时间戳 = **860 个音塞进 58 秒**（15 音/秒，中位间隔 **30.6ms**）。
   在 122.5 BPM 下这比我们求解器的最小砖（15° = 40.8ms）还密 ⇒ 每个音要塞进一格就只能靠
   **变速**（980 BPM），而"每格一个方向"这件事**没有全局目标函数** ⇒
   直拟合给出**二维随机游走**（bbox 58×56 = 2√860，正是随机游走的特征），
   最优化给出**一堆 2×2 闭合金方块**（`自然闭合` 图形偏好把它拆成方块）。
2. **流程层（我的错）**：`core.verify` 只证**按键时刻**对得上（0.0us 全过），
   而**没有任何一步在看"砖块在平面上长什么样"**。于是"对"的标准被我自己偷换成了"时间对"。

### 15.3 修法（已落地）

* **`core/geomcheck.py`（新）**：`metrics(chart)` → 直线率 / 发卡弯 / 回折率 / 平均|Δ角| /
  **非相邻重叠对** / bbox / **每格占地** / 紧凑度；`verdict()` 给「像一条路 / 像一把碎渣」，
  `report_lines()` 直接上屏。阈值保守（每格重叠 >0.35 对 或 每格占地 <8 格² 才判碎），
  格数 <32 不判（不知道就说不知道）。
* **`tools/gen_from_source.py`**：生成报告现在**时序校验 + 几何体检两道关一起打** ——
  这次的教训就是"只打一道关"。
* **`tools/read_adofai.py`**：加同名体检段（读任何一份 `.adofai` 都能立刻判断形状）。

### 15.4 结论与旋钮：`merge_ms` 就是把"碎"换成"直"的那个旋钮

`merge_ms`（③ 采音 · 合并窗口）原本是"间隔小于此值的音并成一次按键"。
对**借用时间戳**这条来源，它的意义变了：**它决定"每秒要出现多少格"**。

| `merge_ms` | 音数 | 几何 |
|---|---|---|
| `0`（时间戳来源的默认） | 860 | ✗ 碎（重叠 1.39/格，占地 3.7 格²） |
| `40` | 551 | ✅ 一条路（重叠 0.05/格，占地 98.6 格²） |
| `60` | 545 | ✅ 一条路（重叠 0.03/格，占地 198 格²） |

★ 实测 `40` 与 `60` **几乎同解**（551 vs 545）——因为这批音本来就落在 **30.6ms 网格**上：
只要合并窗口落在 `[31, 61)` 就是把它们吸到 **61ms（1/8）网格**上；窗口 `>61` 才开始继续吞。
⇒ 这个旋钮其实是**两档**：`<31`（逐音，碎）与 `≥31`（1/8 网格，干净）。

⇒ **借用别人的谱面当采音源时，`merge_ms` 必须 ≥ 半个网格**（本次实测 40~60 都可用）。
它的代价是：原谱 30ms 的 1/16 连打会被并到 1/8 网格上 —— **"轮指"还剩连打的形，但不是逐音**。
**要把"逐音的密集流"做成好看的谱，需要给直拟合加几何目标（最小重叠 + 朝向偏好），
或者显式识别"时长 ≤Xms 的连续段"用固定齿形带铺过去 —— 那是单独一轮的工作。**

### 16.5 已知的坑（别再踩）

1. **`merge_ms=0` + 15 音/秒 ⇒ 几何必碎**（借用时间戳时窗口要 ≥ 半个网格；实测 `[31,61)` 同解）。

4. **`ScaleRadius` 的 `gapLength` 不能是 −1**（游戏 `i += 1+gapLength` 步长 0 ⇒ 死循环）⇒ 代码里 `max(0, 2n-1)`，单测守着。
